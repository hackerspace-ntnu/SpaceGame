# How the game is built

This page is about the machinery around the game rather than the game itself: how a model travels
from someone's Blender file into something a player can walk on, where the shared colour palette
comes from, what all those custom menu items in the editor actually do, and how much of this is
covered by tests (honestly: parts of it, and not the parts you would guess). If you only take one
thing away, take this: **a very large amount of the content in this project is generated by scripts,
and hand edits to generated things are silently destroyed the next time someone runs the script.**
Knowing which things those are is most of what separates a productive week from a lost one.

---

## The journey of a 3D asset

### 1. The source library Unity cannot see

All the Blender masters live in a folder whose name ends in a tilde, which makes Unity ignore it
completely. That is deliberate and has a nice consequence: the sources are versioned alongside the
game, but they have no import records, no ids, and nothing in a scene can accidentally reference
them. It also means you do not need Blender installed to open the project.

The library is split in two. **Components** are reusable parts — 94 of them, filed under structural,
props, mechanical and organic, with variations kept as separate collections inside the same file.
**Models** are assembled deliverables — 42 of them, filed under buildings, characters, creatures,
gear and vehicles. There is an index and a palette document you are expected to read before building
anything, because the fastest way to make an asset is to discover it already exists.

Each source file sits next to the Python script that generated it and usually a short build note
recording what was made and why. A shared geometry helper library supplies the bevelled boxes, tubes,
lofts and rivets that give everything the same visual grammar.

### 2. Why the .blend, not the script, is the source of truth

This is the single most important rule in the art pipeline and it is enforced in code: **the builder
library refuses to overwrite an existing .blend file.** The reason is that the shipped files carry
hand edits that exist nowhere else — an interior somebody built by hand, a rig somebody fixed after
export, geometry someone sculpted. Re-running the generator would destroy work with no record of it.

If you need to know whether a file has been hand-edited, compare object *scales* rather than names;
names survive a hand edit but proportions do not. Several files are known to be hand-built and should
be treated as untouchable: the lander interior, the nomad family, the hexapod creature.

Exports, by contrast, are meant to be re-run constantly. They never write back to the source.

### 3. Export, then automatic import

An export script per model localises the linked palette materials, optionally drops the armature, and
writes an FBX into the Unity-visible art folder. Two things then happen on import without anyone
asking:

- every mesh is forced readable, because runtime NavMesh baking and collider code need to see real
  geometry;
- root-motion curves are stripped from imported clips, because they would otherwise teleport
  rigid-part rigs to the origin.

Those are the *only* two automatic hooks. Everything else in the pipeline is an explicit menu command
by design.

### 4. The prefab is generated, never hand-wired

The last step is a builder script — one per asset family, about 26 of them — that reads the FBX,
composes the prefab, sets the import settings, generates the clips and controller, and saves the
result over the existing prefab. Re-running a builder after a re-export rebuilds everything in place.

Walkable interiors get one extra step: a baked convex decomposition of the collision, because Unity
refuses a concave mesh collider on a moving body. A per-mesh rule does not work here; the fill has to
be baked and then actually checked, ideally by voxel-testing the entrance in Blender before you find
out in play mode that the doorway has an unwalkable lip.

### The traps in the journey

- **Blender FBX arrives at 100× scale.** The centimetre convention means every transform imports with
  a scale of 100 and the mesh data 100× smaller. It cancels out for the model itself, but anything
  sized *against* a socket has to divide by that socket's scale or it comes out a hundred times too
  big.
- **The axis conversion is fixed.** Changing it would silently rotate every new asset relative to
  every existing one.
- **Stale material overrides.** If a re-export changes how many submeshes a mesh has, or their order,
  the prefab's renderer keeps the old material array and renders the wrong thing with no error at
  all. Re-run the builder to re-sync it.
- **A humanoid rig can stop being humanoid, silently.** Re-export a character with a changed
  hierarchy and it simply stops animating, with a completely clean console. Check the avatar's
  humanoid flag after any character re-export.
- **A material freezes the shader defaults it was born with.** When a shader later gains new
  properties, older materials keep whatever the values were at their creation. That is why builders
  rewrite their tunables on every run instead of trusting defaults.
- **Leaf bones are always disabled on export.** Blender's bone tips would otherwise appear as real
  transforms and break every piece of code that walks a skeleton.

## The shared material palette

There is **one palette**, defined in a single Blender file and documented alongside it: 54 materials
across 10 categories — emissive, fabric, foliage, glass, hide, metal, neutral, paint, plastic, wood —
named so that the category is in the name. Nothing in the library defines a local material; every
model *links* to the palette.

The palette started empty and grows on demand, and the tool that adds to it will refuse a
perceptually near-duplicate and tell you the name of the existing material instead. Every entry
carries a note explaining what it is intended for and why it is not a duplicate of its nearest
neighbour. Read those notes before adding a fifty-fifth grey.

**How a mesh actually gets its colour** is worth understanding because one step in it is
counter-intuitive. Face material indices are stamped in Blender from the linked palette slots; the
export makes those linked materials local, because a *linked* material does not survive into an FBX
and skipping that step gives you untextured meshes; Unity then imports the materials as sub-assets of
the FBX itself.

That last part has a consequence that catches people. Because the materials are sub-assets, they are
regenerated on every reimport — so any flag you set on one reverts. That is why the double-sided
variants exist as standalone copies sitting beside the prefabs, refreshed from source on every
vehicle build. Vehicle hulls are modelled as surfaces rather than solids, so without a double-sided
material, back-face culling makes cabins see-through.

Alongside the palette there are hand-authored materials for terrain, portals, surfaces and effects,
121 of them across 13 domain folders. Those are unrelated to the palette and are edited normally.

For scale: the game currently ships **124 imported models** — 35 environment, 34 vehicle, 26 item, 13
creature, 7 weapon, 4 prop, 4 character. Of those, 4 model files plus 24 animation clips are set up
as humanoid; the other 117 are generic rigs — creatures, vehicles, and rigs made of rigid parts
parented to bones rather than skinned. Player animation is retargeted mocap driving one controller
with an upper-body mask for hold poses; creature animation is either authored in Blender or generated
by the builder.

Bought and free asset packs live in their own third-party area and sit outside all of this.

## What the editor tools do

Almost everything above is reachable from custom menu items in the Unity editor. There are three menu
roots, inconsistently — most things sit under one, portals/terrain/environment under another, world
streaming under a third — and one naming convention that is worth internalising:

> **Audit, Report, Validate and Diagnose are read-only. Build, Wire, Apply, Fix and Bake write
> assets.**

Broadly, the tools fall into these families:

- **Prefab builders.** One per creature, vehicle, artifact, weapon-like item, building and menu
  subtree. These read an FBX and write a finished prefab. They also do the paperwork: registering the
  prefab with the networking layer, stamping the save identity, forcing a reimport so the network
  identity actually reaches the file on disk.
- **Content generators.** Item icons (rendered from each item's own prefab at one house camera
  angle), sandstorm noise, rope textures, backpack pack shapes, and materials.
- **World tooling.** Splitting a master scene into 500×500 m streamed chunks and rewriting the
  streaming config, baking all chunk collision into one navigation mesh, checking whether that bake
  has gone stale, and baking a low-poly mesh per chunk for the in-game map hologram.
- **Wiring sweeps.** Adding save identity to every prefab, open scene and chunk scene that needs it;
  adding every networked prefab to the list the networking layer reads; adding ragdoll setup across
  creature and player prefabs.
- **Audits.** Save wiring that would fail silently, mutable state nobody saves, item sizes against
  the shared size ladder, how each item sits in the hand, ragdoll skeletons, and scene objects whose
  source prefab has been deleted.
- **Environment setup.** Installing the volumetric render features into the render pipeline asset —
  which is not a list append, and doing it by hand produces a feature that exists in the asset and
  never runs.
- **Test running.** Running the edit-mode suite headlessly, and building the standalone player used
  for two-machine multiplayer verification.

There are also a handful of custom inspectors that make specific work bearable: scene-view handles
for terrain feature footprints with live preview, a paintable grid for backpack item shapes, a
"generate" button on an AI profile that adds and configures the behaviour modules, and bake buttons
on the terrain and cave tooling.

### The one that costs people days

**Generated prefabs eat your hand edits.** A builder composes a prefab from scratch and saves it over
the existing path. Everything you changed in the inspector — a tweaked value, a dragged reference, an
added component — is gone on the next run, with no warning and no diff you would think to look at.
This has bitten the player ship prefab specifically, more than once. Parts of the main menu scene are
generated the same way, so hand-editing that scene's built subtrees has the same failure mode.

The fix is never "put it back". The fix is: **change the builder.** If a value should be tunable,
make the builder write it; if it should be authored, move it out of the generated region.

A related, quieter version of the same problem: builders write private serialized fields by name. If
someone renames a field in the component, the builder stops setting it and everything still compiles.
There is a helper that at least *warns* when a field name no longer resolves, and builders are
expected to go through it.

And a third: **the asset database goes read-only in some editor sessions and discards prefab and
asset writes without raising anything.** A builder can log a cheerful success having written nothing
at all. The established defence is that a builder ends by re-reading everything it wrote back off
disk and asserting it is really there. Copy that shape; do not trust a silent success.

A few smaller sharp edges live in the same neighbourhood. Several paths are hardcoded on purpose —
the chunk size and output folders in particular, because changing them orphans every existing chunk.
Asset path casing matters and there is at least one folder in the project where the casing drifted.
Deleted prefabs leave blocks in scene files that no component search can find, which is what the
"report missing prefab instances" tool is for. And a stuck networking port can survive the editor's
own teardown, at which point restarting the editor is the only known cure.

## Project settings worth knowing before you write code

Not everything, just the ones that change how you write:

- **Unity 6000.3.11f1, URP 17.3, deferred rendering, linear colour.** Desktop standalone only; the
  mobile render settings in the project are orphans that nothing references.
- **The new input system only.** Legacy input calls compile without a warning and then throw at
  runtime. The bindings live in a generated file that only regenerates when the input asset is
  reimported — editing the asset alone does nothing.
- **Gravity is −18, not −9.81.** Nearly twice Earth. Anything ported from a tutorial or another
  project falls roughly twice as fast as its author intended, and every hand-tuned jump or ballistic
  arc in this repo assumes the higher number.
- **Physics does not auto-sync transforms.** Move something and raycast in the same frame and the
  raycast reads the collider's *old* position unless you sync explicitly.
- **The collision matrix is completely default — every layer collides with every other layer.** The
  named layers in this project are query and presentation tags, not physical separation. Every
  "don't hit X" behaviour is a layer mask on the component doing the query, and that is the pattern
  to follow. Two of the declared layers have nothing on them at all, which means at least one
  "exclude the player" mask in the codebase excludes precisely nothing.
- **Fixed timestep is 50 Hz.**
- **Assets are serialized as text, but not all of them.** The version-control rules deliberately do
  *not* force scene, prefab and asset files to text, because doing so previously let git strip bytes
  out of genuinely binary Unity assets until the editor reported an unhelpable load error. If you add
  a new kind of binary asset, check how git is treating it before committing it.
- **There is no Git LFS**, against roughly 1.1 GB of assets. Know that before adding a large binary.

## How the project is tested

### Everything is edit-mode

There are roughly **1841 assertions across 164 test files**, and every one of them runs in edit mode.
There are **zero play-mode tests and no play-mode assembly at all.** No coroutines, no frames, no
physics stepping. A test that needs time to pass marches the system forward manually in a loop.

The immediate consequence, and the thing that confuses everyone once: **adding a component outside
play mode does not run its startup callbacks.** A component that initialises itself on awake is a bag
of nulls in a test. The standard answer is not to fight that but to route around it — pull the actual
arithmetic out into a plain class and test that. The locomotion policy code is the worked example of
that refactor.

Tests live in two different assemblies that can see different things, and picking wrong is a common
first mistake. One of them is a proper module assembly and can only reach types that live inside the
project's own module assemblies. The other has no assembly definition at all, which is exactly why
most of the suite lives there — it is the only place that can see plain MonoBehaviours, prefabs on
disk, and the asset database.

That second capability produces the most valuable category of test here: **wiring tests**, which load
a prefab from disk and assert that its components and fields are actually connected. They catch the
class of bug where the code is perfectly correct and the asset is not — which, in a project this
prefab-heavy, is most of them.

Fixtures are deliberately thin: a persistence probe that round-trips a prefab through real save text,
a walker rig with real limb proportions, and the multiplayer test-player build. No base classes.

### What is well covered

Roughly in order of density: locomotion and walkers (pure IK, gait and support-plane maths, the
densest suite in the project), items and artifacts, persistence round-trips, vehicles and flight
models, the versus mode and arrival, world streaming and spawning, lobby and menus, netcode
authority, the physical backpack inventory, agents, and portals.

### What is not covered — plainly

These have **zero** tests. Not thin coverage; none.

- **Procedural world generation** — 68 files of terrain generation, settlements, facades and bridges.
  The single largest untested subsystem in the project.
- **Conventional weapons** — firearms, projectiles, ball lightning, the weapon core. (Artifact-style
  items, confusingly, are among the best-covered code in the repo. It is only the conventional
  weapons that are bare.)
- **Audio** — nothing meaningful. No test of the catalog, the FMOD wiring, or emitters.
- **Cutscenes** — one incidental mention across the whole suite.
- **Most of the UI** — the lobby, menus and hotbar are tested; the HUD, nameplates, damage numbers
  and map are not.
- **The rover, cloth, AI perception, and caves** — nothing.
- **Anything that needs a running frame** — because there is no play-mode suite at all. Physics,
  navigation, startup order and frame loops are verified by hand or by the batch-mode multiplayer
  run described below.

That list is not an accusation, it is a map. If you are touching one of those areas, you have no
safety net and should plan for manual verification accordingly.

### Running things

Three levels, cheapest first.

**A headless type-check.** A small script in the repository re-runs Unity's own last compiler
invocation over freshly globbed sources using the editor's bundled compiler. It is fast and it works.
But you must know its limits before trusting a green result: **it only compiles the main assembly.**
It skips every module assembly, all editor code, and *every test file*. A test referencing a type
that does not exist yet still reports no errors — that failure only appears in the editor. It also
needs the editor to have compiled at least once, so it cannot be your first step on a fresh clone.

**The edit-mode suite.** Run from a menu item; it writes a result file with pass/fail counts, one
line per failure, and a final done marker. The runner deletes that file before starting, so **the
absence of the file means "still running" and the presence of the done marker means "finished".**
Poll for it. Never assume.

Two failure modes here look identical from the outside and both are worth recognising. First, a
failing run and a run that never started produce the same silence — hence the delete-then-poll
discipline. Second, **a missing type is a compile error, not a red test**: the entire suite refuses
to run and the test runner reports nothing at all. When you are writing a test first for a type that
does not exist yet, "a compile error naming the type" *is* the failing state you are looking for.

**The two-process multiplayer run.** This is the only real proof that something works for a client
rather than just for the host, and it matters because the failure is asymmetric: the server
instantiates prefabs directly and never consults the network prefab list, so an unregistered prefab
gives you a perfect host and blank clients. There is a menu item that builds a cut-down standalone
player and another that prints the exact commands; you then run one process as host and one as
client, both headless, and grep both logs for an agreed set of reported values. A third mode runs
alone and checks save, quit and load. When you add something networked, the right move is to add one
more reported value to that harness rather than building a second harness.

There are also several validation menu items that are much cheaper than a test run and catch real
defects: validating save wiring, syncing the network prefab list and reading its report, auditing
held item poses and the item size ladder, and auditing ragdoll skeletons.

### Two more things that catch people

- **A persistence round-trip must go through real save text and land on a *different* instance.**
  Restoring onto the same object you captured from passes even when the restore does nothing at all,
  and object-level round-trips hide a serializer stack overflow that only shows up on real text.
- **A mutation in a persistence test must reach a state a player could actually reach**, or the test
  passes without proving anything.
