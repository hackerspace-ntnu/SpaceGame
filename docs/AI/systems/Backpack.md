# Backpack

The physical inventory: a deployable expedition rig whose seven flat faces are cell grids you lay real items onto, rummaged in from a dedicated focus camera.

**Scope:** [`Assets/Game/Scripts/Items/Backpack/`](Assets/Game/Scripts/Items/Backpack) (+ [`Focus/`](Assets/Game/Scripts/Items/Backpack/Focus), [`Placement/`](Assets/Game/Scripts/Items/Backpack/Placement), [`Holders/`](Assets/Game/Scripts/Items/Backpack/Holders)), [`Assets/Game/Editor/Backpack/`](Assets/Game/Editor/Backpack), [`ExpeditionRig.prefab`](Assets/Game/Prefabs/Items/Equipment/ExpeditionRig.prefab), [`expedition_rig.fbx`](Assets/Game/Art/Models/Props/expedition_rig.fbx) / [`.blend`](Assets/Game/Art/Models/_Source~/components/props/expedition_rig.blend).
**Related:** [Inventory.md](Inventory.md) (item defs, hotbar — not repeated here), [Multiplayer.md](Multiplayer.md), [Persistence.md](Persistence.md).

## Model

- The pack is a **plain `Instantiate` per player** parented to the spine bone — not a spawned `NetworkObject`. Contents replicate as *state*, not as objects. Deploy unparents it; reshoulder reparents. They live on the **pack**, not the player: a pack set down keeps its gear.
- An item is `(itemId, PackSurfaceId, uv in metres, yaw)`. No slots, no indices — an index means nothing because a placement carries its own face and position.
- **One global 0.0945 m cell** ([`PackGrid.Cell`](Assets/Game/Scripts/Items/Backpack/Placement/PackGrid.cs)), read off the rig's own webbing pitch. All 8 faces are exact multiples of it (Leaf 8x8, Rack 9x9, LongGoods 18x1, Back 3x6 each — left, right **and centre** — Wings 4x7 each = **273 cells**, zero hem). The centre back panel is the newest and the odd one: it is the oxygen bottle's SOCKET, the only reserved face in the game, and it takes nothing else — see [Oxygen.md](Oxygen.md). Capacity is *cells occupied*, not a count and no longer a raw-area or diagonal test.
- **The rig is sized by [`PackScale.Factor`](Assets/Game/Scripts/Items/Backpack/Placement/PackScale.cs) = 1.05.** One factor on every *length* — cell, faces, the `.blend`, the size each item is drawn at, the focus camera's standoff — and none on any *count*. It is a similarity transform, so 273 cells are still 273 cells, every authored mask is still valid, and nothing about capacity moves. It has moved twice: 1 -> 1.5 on 2026-09-01 for readability, then **1.5 -> 1.05 on 2026-09-02** (30% off) because the 1.5 rig was too big to wear. See [Scale](#scale).
- **The gear wall does NOT ride `Factor`.** Its drawn size is pinned in the original frame by [`PackScale.WallDrawn`](Assets/Game/Scripts/Items/Backpack/Placement/PackScale.cs) = **1.908** (`WallModel` 1.59 baked in the model x the 20% enlargement decided 2026-09-02), and `WallDisplay` is *derived* as `WallDrawn / Factor`, so resizing the backpack leaves the ship's fitting byte-identical. Unlike `Factor` it moves nothing but pixels — see [Drawn frame vs logical frame](#drawn-frame-vs-logical-frame).
- Each item fills a **mask** ([`PackShape`](Assets/Game/Scripts/Items/Backpack/Placement/PackShape.cs)) — authored in [`PackShapes.asset`](Assets/Game/ScriptableObjects/Items/PackShapes.asset), else derived by ceiling its measured footprint to whole cells. Masks let two L-shapes interlock.
- Layout logic ([`PackLayout`](Assets/Game/Scripts/Items/Backpack/Placement/PackLayout.cs), `PackGrid`, `PackShape`) touches no `UnityEngine` beyond `Vector2`, so EditMode tests drive it as plain C#.

## Flows

**Open.** 1) B → `PackFocusSession` + `BackpackController.Toggle` both fire. 2) Toggle only *asks* (`NetMsg.PackState`, request verb). 3) Server re-checks state, runs **its own** ground probe, `Commit` + broadcast. 4) Every machine plays the toss arc, then the unfold. 5) The focus camera flies in 0.15 s later without waiting for the unfold.

**Pick up.** 1) `PackPointer` ray on the `PackItem` layer names the display copy. 2) Left click → `Lift`: purely local, nothing sent — the layout still holds the item; `SetInHand` just stops the pack drawing it. 3) `originGrab` is `AnchorUv` (a cell the item *fills*), not the stored block-centre uv.

**Place.** 1) Every frame `PackLayout.Snap` grid-snaps the cursor uv for the current shape+yaw; `CanPlace` judges *exactly* those cells. 2) `PackGridVisual` paints the footprint green/red plus the whole face's free/taken lattice. 3) Click on green → `LetGo`, then `RequestMove` (from pack) or `RequestStow` (from hotbar) — **nothing moves locally**. 4) Server resolves the grab point positionally, applies, and the `NetworkList` rewrite moves everyone's display. **A RESERVED face is advertised as well as judged**: every frame something is in hand, `PackContainer.SocketFor` asks whether any face is reserved for it, reachable and free, and `PackGridVisual.ShowSocket` lights that face's cells in the legal green at a third alpha — wherever the cursor is, and never on the face under it, where the ghost is the better answer and both fills share one `Lift`. Today that is one face and one item: the oxygen bottle's socket. Every other readout here answers "can this land HERE", which only helps a player who already guessed the right face, and the socket looks exactly like the two ordinary back panels beside it — so this is a signifier for a face with none of its own (`GDC-L1-UX-0004`) at a salience deliberately under the cursor's verdict (`GDC-L1-UX-0003`). It shares the ghost's green on purpose (one learnt colour, not two) and is told apart by SHAPE, not hue: ringed-and-filled cells like the lattice against the ghost's full-bleed quads — which is what keeps a third green off `GDC-L1-UX-0003`'s "never colour alone" list. The pack still has no non-colour channel for legal-versus-refused; that gap is real, pre-existing, and not widened here. `PackSocketInviteTests`.

**Swap.** A full hotbar is not a refusal. `TryTakeToHotbar` puts the pack item in the selected slot and the displaced one back on the pack (same face, then first-fit on that face). A drag onto a *named* slot goes through `BackpackController.TakeIntoSlot`, whose fallback is `TryStow` across every reachable face; `CanTakeToHotbar` predicts both branches so the preview cannot approve a drop the server refuses.

**Flip the leaf.** The one held gesture in focus mode: grab bare board, drag through the arc, release past halfway to commit (`PackLeafDrag`, `BackpackObject.ScrubRack`/`SettleRack`). R is the same thing as a toggle. It only fires where the item hit found nothing.

**Refuse.** There is no message and no cursor change: red cells *are* the refusal. A click on red turns the item a quarter — the refusal and its usual fix are the same click. A symmetric shape with no turn to offer gets a timed flash instead. A click off the faces turns silently. World pickups that overflow use first-fit (`TryStow` → `TryArrange`) across *reachable* faces only.

## Scale

One constant, [`PackScale.Factor`](Assets/Game/Scripts/Items/Backpack/Placement/PackScale.cs) = **1.05**. Everything below moves with it; anything that does not is a bug. It has moved twice — 1 -> 1.5 on 2026-09-01, and **1.5 -> 1.05 on 2026-09-02, a 30% reduction**, because the 1.5 rig was too big for a thing worn on a back. **Changing it is five edits in one commit**, and four of the five fail silently on their own:

| Length | Where it is written | Now (at 1.05) |
| --- | --- | --- |
| The cell | `PackGrid.Cell` (a literal; `PackScaleTests` asserts it equals `LegacyCell * Factor`) | 0.0945 m |
| The 7 rig faces | `ExpeditionRigWiring.SurfaceTable`, mirrored in `PackGrid`'s doc table | Leaf 0.756², LongGoods 1.701x0.0945, Rack 0.8505², Back 0.2835x0.567, Wings 0.378x0.6615 |
| The rig model | [`expedition_rig_scale.py`](Assets/Game/Art/Models/_Source~/components/props/expedition_rig_scale.py)'s `SCALE`, a third pipeline step after generate + dress. **Composes** against its `rig_scale` stamp, so a change applies only the residual | deployed 1.81 x 2.19 x 0.87 m |
| Every item on the mat | `ItemFootprint.Measure`, once, on `ItemGrip.PackSize` | x1.05 |
| Focus camera standoff | `PackFocusCamera.DistanceOut` / `HeightUp`, via `PackScale.Apply` | 2.583 m / 1.575 m |
| Mat decoration | `PackGridVisual`, `PackStrapVisual`, `PackHandVisuals` widths and lifts | x1.05 |
| *(not this factor)* the gear wall's **drawn** board | `PackScale.WallDrawn` = `WallModel` (1.59, = `inventory_wall_scale.py`'s `TOTAL`) x the builder's root scale (1.2) | decided per-wall, invariant under `Factor` — see [Drawn frame vs logical frame](#drawn-frame-vs-logical-frame) |

What deliberately does **not** move: every cell *count*; every angle (`PitchDown`, `Fov`, yaws); `ItemGrip.holdSize` and `packSize` themselves — the item in the hand is exactly the size it was; `BackpackController.deployDistance` / `arcHeight`, which belong to the player's body rather than the pack; the gear wall's drawn board; and `pack_holders.blend`, because `HolderBuilder` stretches every holder to fit through `ItemFootprint.SizeOf` and so follows on its own.

**A move of the factor does not change how big the pack looks in focus mode** — the camera's standoff rides it too, so the mat fills the frame identically, by construction. What changes is the rig in the *world*: on the player's back, and standing on the sand. Wanting a smaller mat on screen is a change to `PackFocusCamera`'s own numbers, not to the factor. Design basis: the 1.5 enlargement bought glanceable readability on the mat (`GDC-L1-UX-0003`) and a bigger target for the one gesture focus mode has (`GDC-L1-UX-0004`, `GDC-L1-UX-0007`) — and none of that is given back by the shrink, for that same reason. What the 1.05 shrink buys is the *world* reading honestly: a 1.215 m board and a 2.43 m lash line on a walking person read as a market stall rather than as a pack, and a diegetic object that contradicts its own use is a break in the fiction the physical inventory exists to sell (`GDC-L1-FEEL-0007`, whose caution is to keep the simulated space self-consistent — which a uniform factor satisfies at any value, so the choice between them is a readability judgement, not a correctness one). It also narrows, without removing, the worn-pack intrusion in first person (see Gotchas). An item is still exactly as many cells as it was, at every factor.

### The wall and the room

The gear wall is the one place the 2026-09-01 enlargement moved a **count**, because it is the one surface that has to fit inside something. Enlarged in place its fitting came out **8.46 x 4.95 m** and the lander's aft room has neither dimension. **Measure against the baked collision, never against the ribs you can see.** [`player_ship_collision.fbx`](Assets/Game/Art/Models/Vehicles/PlayerShip/player_ship_collision.fbx) is a convex decomposition, and the hull skin `Plane.001` curves up off the deck — its hulls fill that curve, so the outboard half-metre of deck is solid to a player for the first ~0.36 m up while nothing is drawn there. At the old `WallRibClearance` 0.70 the fitting's feet, plinth and tray stood inside it down the whole room. The footprint comes clear at 0.95 m, so the clearance is now **1.00 m**, and at that standoff the headroom over the footprint is **4.37 m** (capped by one arch-rib buttress, `Cube.007`; the deckhead proper is 4.79-4.87 m). The builder centres the fitting on the main deck's centre, which leaves 2.91 m of run forward of it and 3.75 m aft. So the grid was re-cut, in whole six-cell bays across, from `60 x 30` to **`30 x 22`** — 1800 cells to **660**. That cut is still the capacity, and the fitting's size in the room has not moved since — not even when the backpack shrank 30% on 2026-09-02, because the wall's drawn size is pinned by `PackScale.WallDrawn` rather than derived from the pack. As it stands the fitting is **5.610 x 4.923 m** (30 x 22 cells at `PackScale.WallDrawn` = 1.908 over the original frame — the 20% enlargement decided 2026-09-02), and its placement is **authored**: the user hand-placed it (face centre ship-local **(2.49, 5.45, -0.58)**, plinth sunk 0.116 m into the deck, back and header deliberately tucked into the hull's baked convex fill), and `PlayerShipBuilder.WallPlacementNudge` bakes that pose as an offset from the measured target so every rebuild reproduces it — a hand move left only in the prefab is discarded by the next rebuild; restate the nudge instead. The drawn face and every cell stay clear and aimable (measured, and guarded by `PlayerShip_InventoryWallFaceIsAimableFromTheRoom`). `WallGridCentreHeight` and `WallDepth` are *derived* from `WallDrawn`, so a resize re-places the wall on the next ship rebuild with nothing retyped. That is a real cut in storage, taken knowingly. A fitting that stands *in* the room reads as part of it; one that clips the deckhead or sinks into the hull destroys the room's legibility, and the deck is the one interior space the player learns (`GDC-L1-LEVEL-0002`, contextual/4). The wall is also read at a glance from across the deck, which is what the 1.5x cell was for in the first place (`GDC-L1-UX-0003`, objective/4) — a bigger cell over a smaller board still wins that trade. The cost is honest and not a design gain: this is a **base store**, deliberately generous, not a scarcity dial, and `GDC-L1-ECON-0002`'s own exception covers exactly that — so 1800 -> 660 is a constraint accepted, not tension bought. It only starts to bite if playtests show the wall filling up; the fix then is a second wall or a bigger room, never a face that does not fit. Nothing is lost from an existing save — see [Persistence](#persistence).

### Drawn frame vs logical frame

`PackScale.Factor` (1.05) and the gear wall's `PackScale.WallDrawn` (1.908) are **not the same kind of number**. `Factor` moves the cell, so it moves every stored uv's meaning and needs a save migration; the wall's enlargement moves nothing but pixels, applies to the gear wall alone, and is applied in exactly three functions — `PackSurface.ToLocal`/`ToWorld`/`ToUv`.
- The **logical frame** is `PackSurface.Size` and its cells — 30 x 22 of `PackGrid.Cell`, 660 — and is what every placement, save byte and wire message is written in. The display scale never touches it, which is why the wall alone needs no version bump and nothing to migrate. Note the logical frame's *metres* do ride `Factor`, because the cell does.
- The **drawn frame** is that times `PackContainer.DisplayScale`. The three conversion functions speak it, so the model, ghost cells, hover lattice, display copies, holders, straps and the face `BoxCollider` grow together — and the aim, which resolves through `ToUv`, still lands on the cell under the crosshair.
- **`WallDrawn` is stated, `WallDisplay` is derived** (`WallDrawn / Factor`), so the wall's real on-screen size belongs to the *wall* and is invariant under any resize of the backpack — which is what let the 2026-09-02 rig shrink leave the ship's fitting untouched. Typing a literal into `WallDisplay` re-couples them, silently; `PackScaleTests.TheGearWallIsDrawnTheSameSizeAtAnyPackFactor` says so. **One size, met from two sides.** The model's geometry carries `WallModel` = 1.59 baked in (`inventory_wall_scale.py`'s `TOTAL`, applied as the residual against the `wall_scale` stamp); `InventoryWallBuilder` scales the prefab ROOT by the residual `WallDrawn / WallModel`; and `PackScale.WallDisplay` scales the uv->world mapping. The two frames must agree — the bay dividers are six cells apart and the webbing on a two-cell pitch, so a mismatch puts every line out of step. The root scale is safe *only because* every consumer (`ToLocal`/`ToUv`, `BackpackItemVisual`, `HolderBuilder`, `PackStrapVisual`) divides `lossyScale` back out and follows `DisplayScale` instead — scaling anything they do not divide out (the surface's own local scale) is the silent double application.
- **The room's measured budget on `WallDrawn` is 1.602, and since 2026-09-02 the wall deliberately exceeds it.** In the original frame the fitting is 2.580 m tall, and the 2026-09-02 ship offers 4.383 m over its footprint (baked collision, at `WallRibClearance`); with the old 0.25 m gap that allowed `(4.383 - 0.25) / 2.580` = **1.602**. The user chose a 20% larger board (1.908) over the clearance, then hand-placed the fitting with its back and header tucked into the hull's baked convex fill (`WallPlacementNudge`) — the drawn face and every cell stay clear and aimable (measured on the rebuilt prefab). The guards changed meaning with the decision: `WallInventoryTests.TheWallIsDrawnAtItsDecidedSize` pins the size constant, and `PlayerShipTests.PlayerShip_InventoryWallFaceIsAimableFromTheRoom` guards the thing that must actually hold — a ray from a standing eye to any cell reaches the wall first. ("Headroom over the footprint", which the old guard measured, means nothing once the footprint's outboard strip is inside the fill: rays start inside the convex hulls and report their underside as the roof.) An earlier 1.8285 was an over-scale nobody decided, left both old guards failing as "an accepted cost" and was reverted the same day — the difference between that and this is that the decision, the measurement and the guards now agree in the same commit. A bigger board without intrusion means fewer ROWS (`SurfaceCellsUp` **and** `inventory_wall.py`'s `GRID_H`), which needs the `.blend` REGENERATED, destroying its hand edits.

## Multiplayer

| --- | --- |
| Contents (`PackLayout`) | **Server**. Clients never write; `BackpackNetwork` republishes the whole list on `OnChanged` and clients `AdoptPlacements`. |
| Deploy state + drop pose | **Server**, via `NetMsg.PackState` (A = state or `-1` ask, B = request/announce verb). Ground probe is the server's — clients never stream their own chunk. |
| Rack (leaf up) | **Owner-written `NetworkVariable`**. Not contested; focus mode already requires ownership. |
| Take / move / stow | Client asks on the **pack owner's** channel (`PackTake` 68, `PackMove` 76, `PackStow` 78); all handlers are idempotent and positional. |
| Lift into hand | Purely local — no request, no undo needed. |

Nothing about `PackScale.Factor` crosses the wire. `PackPlacementWire` carries a uv in metres, and both machines derive that uv from the same `PackGrid.Cell` and the same `SurfaceTable` compiled into the same build — so host and client agree by construction at any factor, and a mixed-version session was never supported. `PackSurfaceId` values are untouched: neither resize renumbered anything. The wall's `WallDisplay` is even further from the wire — it is a serialized field on one prefab, read only by the drawing code. `WallAimController` and its static `Aiming` claim are **purely local and owner-gated** (`Network.Owns(this)`, and the component is disabled on a replica): which verb the Use button carries is a question about *this* screen, while the stow and the take that follow are requests the server decides.

Other players see the rig, its unfold, every placed item's display copy, holder and straps. An item in someone's hand is hidden on **their** machine only (`SetInHand`); remotes still see it lying on the mat until the server accepts the move.

## Persistence

- `BackpackSaveable` sits on the player (`[RequireComponent(BackpackController)]`), key `backpack`; the format is `BackpackSaveCodec`, testable without a prefab.
- **v4** record = `version (4), itemId, surface (byte), u, v, yaw` + `deployed`/`packPosition`/`packRotation`. Footprints are **never** stored — recomputed from the prefab, so resizing an item does not stale a save.
- **There is one file version per value of `PackScale.Factor`**, because `u`/`v` are metres — not normalised coordinates and not cell indices. `PackSaveCodec.UvScaleFor` brings an old payload forward by `PackGrid.Cell / (that version's cell)`, which lands each item on the *same cell* it was saved on: scaling a surface and its uv by the same factor is exactly cell-preserving, and `PackScaleTests` asserts it over every origin on an 8x8 face, for every frame. Without it nothing would be lost (the first-fit fallback below catches it) but the player's gear would silently rearrange itself. The frames so far: no `version` key or `<= 2` -> `PackScale.LegacyCell` (0.09); `3` -> `PackScale.EnlargedCell` (0.135); `4` -> today. **Note the v3 migration is a *divide* (x0.7)** — the 2026-09-02 shrink is the first one that made a save smaller, and a migration table written as "older means multiply up" passes the v2 test and corrupts every live world.
- Restore places each item back exactly, else falls back to `TryArrange` first-fit; only a total failure logs and drops it. A payload with no contents keys at all leaves the pack alone (old saves must not be emptied).
- **Shrinking a face needs no file version, and loses nothing.** The wall's `30 x 22` re-cut put every old placement past its far edge outside the face; `TryPlace` refuses, first-fit catches it, and the item comes back somewhere else on the wall. `WallInventoryTests.GearSavedNearTheOldWallsFarEdgeComesBackOnTheSmallerWall` pins that, because a shrink that silently deleted the far column would look exactly like one that worked. The guarantee is *somewhere legal*, not *where you left it*.
- **The wall's *drawn* enlargement needs no file version and no migration at all**, unlike `Factor`'s. It lives entirely in the drawn frame, so a wall save written at one `WallDrawn` is byte-identical to one written at another and reopens on exactly the same cells. `WallInventoryTests.AWallSaveDoesNotNoticeTheEnlargementAtAll` asserts both directions — same JSON, same uvs back. The wall's *logical* frame is a different matter: it rides `PackGrid.Cell` like every face, so a wall save takes the same `UvScaleFor` migration a pack save does. Both go through `PackSaveCodec`, which is why there is one migration and not two.
- v1 (`strapItemIds`/`mainItemIds` compartments) migrates through first-fit. Free-placement uvs and 24°/45° yaws from before the grid land on the nearest cell/quarter-turn — no second file version.
- Redeploy is deferred to `OnLoadComplete` and goes **straight to the settled pose**, never through an arc.

## Gotchas

- **The rig is a solid body in exactly one situation: standing still on the ground.** Worn is off (it would join the wearer's own compound collider) and **in flight is off**, and the second one is a bug fix. [`ExpeditionRigWiring.EnsureBodyCollider`](Assets/Game/Editor/Backpack/ExpeditionRigWiring.cs) fits the box to the **unfolded** rig — 1.81 x 0.87 x 2.19 m — and nothing on the rig is a Rigidbody, so off a back it is a STATIC collider. It reaches 1.58 m along +Z, which the landing rotation points AT the wearer, while the toss starts 0.45 m in *front* of them: switched on there it encloses their 3 m capsule and the shallowest way out is straight DOWN, 0.84 m of it. PhysX drives them that way — into the sand outdoors, where terrain shoves them back and nobody notices, and clean through any built floor, which is the whole of *"I put my backpack down inside the spaceship and spawned under the spaceship"*. `BackpackObject.SetFlying` composes with `IsWorn` in one place, `RefreshBody`; the stow flips it at the *flight*, not at the fold, because a pack folding on the sand is still standing there. Note that `BackpackDeployArcTests.TheToss_StaysInFrontOfThePlayerForTheWholeFlight` only ever measured the pack's **origin** against a 0.30 m body radius — a clearance test on a transform is not one on a collider, and that gap is where this lived. Pinned by [BackpackSolidityTests](Assets/Game/Tests/Editor/BackpackSolidityTests.cs).
- **The Use button on a gear wall belongs to the WALL, for both of its verbs.** A press there is a stow or a take, never a trigger pull, and `EquipmentController.OnUse` returns early on `WallAimController.Aiming != null`. That claim used to be made only while a *placement ghost* was up (the static was called `Placing`), so the take verb shared the button with the hand: clicking an item lying on the wall lifted it off **and fired whatever the player was holding, point-blank at the wall**. The rule now lives in one argument-only function, [`WallAimController.WallOwnsUse`](Assets/Game/Scripts/Items/Wall/WallAimController.cs), decided once per frame in `Update` before either readout draws — not inside the readouts, which is how the two came to disagree. Note the layering: the claim is the *second* line of defence. The first is that **an item on an inventory surface is not an item at all** — [`DisplayCopy.Strip`](Assets/Game/Scripts/Items/Equipped/DisplayCopy.cs) takes every MonoBehaviour off a display copy, so there is no `UsableItem` on it to fire. Never "fix" a stray use by swallowing the input at the item. The same bug has a second entrance: **`PackPointer.TryHitItem` is an unoccluded cast over one layer, so a hit on it says nothing about what the crosshair is on** — it finds the nearest `PackItem` collider on the ray at any range, including gear on a rig deployed in front of the wall and on the player's *own worn pack*. `Resolve` used to `return false` on a hit belonging to something other than a wall, dropping the readout and the claim with it; it now falls through to the surface raycast.
- **A worn pack is hidden from its own wearer's camera, and nothing about that is tunable geometry.** `BackpackController` registers `Pack.GetComponentsInChildren<Renderer>(true)` with [`PlayerLook.SetWornHidden`](Assets/Game/Scripts/Characters/Player/Movement/PlayerLook.cs) — 35 renderers on the bare rig, more with gear — and clears it again. Three call sites, all reading `Pack.IsWorn` so none of them has to agree about which of the four states counts as "on the back": `SnapToWorn` (on), `StartDeploy` (off, at the FIRST frame of the toss — the toss is staged in front of the player so they watch it, so it must be visible for the whole flight and not from the landing), and `OnPackVisualsRebuilt` (the gear, which is instantiated under the rig long after either). **Do not try to fix an intruding pack by moving `wornLocalPosition` instead.** The pack rides the `Spine` bone while the camera is bolted to the player root at `(0, 1.45, 0.16)`, so a walk cycle's lean rotates it about a pivot below the eye and throws its top forward through the near plane — and `LongGoods` takes an item **18 cells** long, so no worn pose survives gear the player chose the size of. The 2026-09-01 `PackScale.Factor` enlargement is what first pushed it past the threshold — the stowed board went from 0.81 m to 1.215 m — and it is the reason the factor was cut 30% on 2026-09-02, which brings the board back to **0.8505 m** and the lash line to 1.70 m. That narrows the intrusion; it does not remove it, because the pivot argument above holds at any size. `wornLocalPosition` has still never been re-tuned, which is a real and separate thing to look at from *outside* first person.
- **Only one focus camera may hold the player's eye, and [`FocusCamera`](Assets/Game/Scripts/Presentation/Cameras/FocusCamera.cs) enforces it with a static `holder`.** A fly-out hands the eye back only when it LANDS, so for its whole duration the player's own camera is switched off while nothing claims to be using it — and the player can act in that window (B again, or F for the body screen). A second camera starting there would capture `enabled == false` as "the player's state" and faithfully restore it on exit, switching their own view **and ears** off for good; the only accidental recovery in the game is mounting and dismounting a vehicle. `TakeOverFromPlayerCamera` therefore dismisses the incumbent first, which is also what stops two enabled cameras sharing a depth and two `AudioListener`s. Three siblings of that rule: **the restore is gated on `tookOver`** — the old `PackFocusCamera.Dismiss` wrote the saved flag unconditionally, so an Esc inside the 0.15 s pre-handover delay left *no* enabled camera at all, a black screen (`Settled` is likewise false until the handover, or a caller gating on it draws one frame at the player's eye); **`FlyOut` must not `StopAllCoroutines`**, because a subclass is the same MonoBehaviour instance, so the flight is tracked by handle; and **a runtime `VolumeProfile` does not clean up its own components**, so `Dismiss` destroys the `DepthOfField` as well as the profile and nulls the field, since `Destroy(gameObject)` is deferred and `LateUpdate` can still run — and write to it — in the same frame.
- **An outline material may not be shared between two shells, and its clamp bounds are `PackScale.Apply` of a `const`.** `OutlineShell.Build` writes `_OutlineWidth` onto the material it is handed, computed from the traced visual's own size, so two visuals tracing from one material both render at whichever width was written last — the pack is safe only because hover and denied are separate materials, and each `BodySite` owns three of its own for the same reason. `MinOutlineWidth`/`MaxOutlineWidth` are `static readonly` initialised from `PackScale.Apply(<const>)`; if `PackScale.Factor` is ever made mutable, a type initializer running at a different moment would silently retune every outline in the game, and invisibly, because `Build` overwrites the seed before the first draw. **Accepted layering wrinkle:** `SpaceGame.Presentation.FocusCamera` reaches into `SpaceGame.Items.BackpackItemVisual.ItemLayer` for its volume layer, so the *body* screen's blur volume also sits on the layer named `PackItem`. It compiles because neither folder has an asmdef; the day either gets one this is the thing that breaks, since an asmdef cannot reference Assembly-CSharp.
- **A display copy's collider is for QUERIES ONLY, and says so with `excludeLayers = Physics.AllLayers`.** [`BackpackItemVisual.Build`](Assets/Game/Scripts/Items/Backpack/BackpackItemVisual.cs) adds the one `BoxCollider` the cursor ray needs after `DisplayCopy.Strip` has taken every collider *and the Rigidbody* off the copy — so that collider joins the nearest body **above** it: on a worn pack the **player**, on the ship's gear wall the **ship**. Left in the simulation it is precisely the fault `BackpackObject` switches its own body collider off to avoid ("bolt a box onto the player's own capsule and wedge them in every doorway they fit through"), except once per stowed item and at the size the item is *drawn* (`PackSurface.DisplayScale`, so a shade larger again on the wall). The gear wall is where it became obvious — a wall stands in a room people walk through — but the worn pack had it first, and it is why walking around inside the ship went wrong the moment there was gear on the wall. Not a trigger and not a layer-matrix row: a trigger still reports contacts and still belongs to that compound body; the project's matrix is fully open and closing the `PackItem` row would miss the copies that fall back to the rig's own layer when there is no such layer; and switching the collider off takes the cursor ray with it. Queries do not consult `excludeLayers` — [`PackItemVisualTests`](Assets/Game/Tests/Editor/PackItemVisualTests.cs) pins all three halves. **And the layer assertion is not the guard.** It shipped as one for a day: `Assert.AreEqual(Physics.AllLayers, box.excludeLayers.value)` tests the *edit*, not the outcome, and how a collider's `excludeLayers` composes with the masks of the Rigidbody it hangs under is a rule this project does not own and Unity has changed before — so the mechanism could stop working with every test still green. The guard is `ADisplayCopyDoesNotShoveTheBodyItHangsOn`: a real body, a bulkhead stood half inside the copy and nowhere near the body's own collider, `Physics.Simulate` stepped by hand (`SimulationMode.Script`, the idiom `WalkerPlatformCarrierTests` established), and the body must not have moved. It asserts `box.attachedRigidbody` is the wearer **first**, because a fixture where the copy hung off nothing would pass the shove for the wrong reason. Beside it is `TheControl_ACopyLeftInTheSimulationDoesShove`, which clears `excludeLayers` and requires the shove to appear: without it a mis-seated bulkhead or a simulation that never stepped reads exactly like a fix.
- **The magnet is gone.** `CanPlace` answers about the exact cells drawn, never a nearby spot. Do not reintroduce "find the nearest legal spot" — comments and [BackpackStowTests](Assets/Game/Tests/Editor/BackpackStowTests.cs) exist to keep it out. The ghost cache is keyed on `(surface, cell origin, legal, rect dims)`, and masked shapes bypass the early-out entirely because `Rotated` allocates a new pattern per call. And ignore the class-level comments that still say "the limit is surface area": that is legacy prose from the pre-grid design, and the real limit is cell occupancy.
- **`Reaches` gates player paths only.** `TryPlace`/`AdoptPlacements`/`StowAuthored` deliberately ignore it, or a restore onto a worn pack (every pack is worn in `Awake`) would lose everything not on the Rack. `Rack` is the *only* face reachable while stowed; the leaf, lash line and both wings ride `PIVOT_Leaf` and vanish when racked. **One face is RESERVED, and it is the only one.** `PackSurfaceId.BackPanelCentre` is the oxygen bottle's socket — the pack is plumbed into whatever stands there, so a rifle in it would be plumbed into nothing. `PackSurface.AcceptsOnly` names the items a face takes, empty meaning "anything that fits", and the rule is consulted on EVERY path that chooses a face: `TryPlace` (which is the restore primitive, so an old save naming something else falls through to first-fit rather than putting it back), `TryMove`, `TryArrange`, both halves of a hotbar swap, and both drag ghosts — a rule enforced on the placement but not on the preview is a green cell that does nothing. **`PackSurface.AcceptsItem` answers two questions, not one**: what this FACE will hold (`AcceptsOnly`) and what this ITEM will stand on ([`ItemGrip.ConfinedToSurfaces`](Assets/Game/Scripts/Items/Equipped/ItemGrip.cs) — see the wing pack gotcha above). Both are empty on almost everything, so it stays a cheap early-out; putting the second one anywhere else would mean finding all nine call sites again. **Ask it of the ASSET, never of an id**: `PackHandController.HeldItemId()` is deliberately null for a hotbar lift, so the ghost used to ask `AcceptsItemId(null)` and get "no face objects" for every drag out of the bar — which painted the bottle's own socket red for the bottle, and would have painted a confined item green on faces the server refuses. The two overloads answer identically now, but only the reference one can answer for an item authored outside `Resources/Items`, which `PackContainer.known` can hold and the registry cannot resolve. `TryArrange` additionally runs a reserved-faces pass FIRST, or the bottle first-fits onto the mat and its socket stays empty, which looks perfectly fine. See [Oxygen.md](Oxygen.md).
- **The layout is keyed by item ID — and a container can hold an ID the registry has never heard of, while a hotbar cannot.** The same asset can never be in the pack twice (lifts from the hotbar are refused up front rather than dying at the drop). And `PackContainer.ItemFor` answers from its own `known` cache of direct references before it ever asks `Registry<InventoryItem>`, so a starting item authored from *anywhere* displays and hands over fine — but the hotbar stores nothing except the `ID` and resolves every read through the registry, which only loads `Assets/Game/Resources/Items`. A take of such an item used to "succeed" and then every read of the slot resolved null: gone from the mat, never in the bar, no reload brings it back. That is exactly how the ExpeditionRig's whole starting roster, authored against the dead duplicates in `Assets/Game/ScriptableObjects/Items/`, was lost one take at a time (fixed 2026-09-02 by repointing the prefab references). [`PackContainer.HotbarCanResolve`](Assets/Game/Scripts/Items/Backpack/Placement/PackContainer.cs) now refuses such a take loudly while the registry is populated (an empty registry — EditMode tests, bare scenes with no `RegistryLoader` — is exempt, and test fixtures register their synthetic items), and [`PackStartingItemTests`](Assets/Game/Tests/Editor/PackStartingItemTests.cs) sweeps every shipped `PackContainer`'s starting lists for items outside `Resources/Items`.
- **Holder FBX axes are baked, not rotated.** `pack_holders.fbx` imports with `bakeAxisConversion: true` and `ExpeditionRigWiring.NormaliseRoot` folds any residual root rotation into children. `HolderBuilder` stretches a holder non-uniformly and counter-scales `HARD_` children componentwise — that inverse is only valid when axes agree, so a rotated `HARD_` empty comes out sheared.
- **An item with no `ItemGrip` measures its raw mesh bounds** (one shipped prefab came out 11 m and filled the screen). `ItemFootprint` warns once per prefab past 2 m. `PackSize` falls back to `HoldSize`, whose default 0.30 m must stay equal to `EquipItemSocket.DefaultHoldSize`.
- **The footprint cache never expires by itself** — [`ItemFootprintCacheInvalidator`](Assets/Game/Scripts/Items/Backpack/Placement/Editor/ItemFootprintCacheInvalidator.cs) clears it on asset import. `PackShapeLibrary` re-indexes on `OnValidate`.
- **An item keeps its own up, and that decides which faces a TALL item can use at all.** `FootprintOf` is *defined* as `(size.x, size.z)`, and `BackpackItemVisual.Build` turns a copy only about the surface NORMAL and lifts it half its own height along it — so an item's height is never part of what a face reserves, and a face cannot ask for a different up. On a horizontal face a bottle stands on it; on a VERTICAL one — either back panel — the same bottle points straight out of the wearer's back by its whole length. That is a design constraint rather than a tunable, and there are only two answers to it: put the item on a face whose normal is up, or **lay the item down in its own prefab** so its length is in the footprint and its short axis is the one that stands off the face. The oxygen bottle takes the second (`OxygenGearBuilder.BottleLiesDown`, with the inverse in `rotationOffset` so the hand pose does not move) and therefore lies flat against a back panel, which is what a 0.5 m bottle on a pack should do — see [Oxygen.md](Oxygen.md). Separately, a prefab that lies down wrong is authored data — fix it with [`ItemPackOrientation`](Assets/Game/Editor/Backpack/ItemPackOrientation.cs), not at seating time. For a **builder-owned** prefab the turn goes in the builder instead, or the next run swallows it without a word — [`JumpingRodBuilder.LieDown`](Assets/Game/Editor/Items/JumpingRodBuilder.cs) is the worked example — and it turns the CARRIED prefab only: `JumpingRodDeployed.prefab` is a planted pogo stick, must stay standing, and the hop hangs it by a *measured* `bounds.min.y`, so laying the carried one down cannot reach the bounce. Either way, compensate `ItemGrip.rotationOffset` by the inverse: `rotation = handRotation * Euler(offset)`, so turning the contents by R and the offset by R inverse multiplies back out and **the pose in the hand does not move**.
- **"Smallest axis up" is not the same as "the way you would put it down".** Maximising the resting face is right for a slab, a pole or a board and wrong for anything with a grip, a sight or a foot: a rifle set on a table rests on its magazine, not on its side. And even where the axis is settled the SIGN is not — +90 and -90 about X both lay an item down and one of them lays it down upside down. `Tools/SpaceGame/Items/Audit Pack Orientation (whole roster)` prints the measurement and names the candidate axis; the sign is decided by looking.
- **The axis and the sign are both decidable off the mesh — go and measure before turning anything.** Neither needs the Editor: drive Blender headlessly over the `.blend` in `_Source~/`, or over the FBX for a model with no source, and read the geometry. Two settled cases, both done that way:
  - **`PortalGun` is NOT mis-oriented, however the audit reports it.** It is a fire extinguisher, so its longest axis is its own up and the audit says "STANDS ON END". It has a **foot**: 0.0130 m² of down-facing geometry in the bottom 5 mm of the mesh, an annulus from r 0.018 to r 0.0505 m against a bottle radius of 0.0589, and `portal_gun.py` puts the origin at the centre of that ring so the bottle "stands on a surface without a Z nudge". Laying it down turns 4x9 cells that fit the rack strictly into 14x9 that fit nothing, which `PackOverhang` then lashes ski-fashion across **every one of the rack's 81 cells** — a third of the rig for one item. And the sign is undecidable in any case: the mesh is mirror-symmetric about X to within 0.07% of face area (+X 0.042826 m², -X 0.042858 m²), so the only thing the choice picks is which sight tube gets buried. `PortalGunWiringTests.TheGunStandsOnItsBaseRing` pins it, and `PortalContentBuilder` carries the numbers. What genuinely read wrong there was the **size**, and it is fixed: through the `packSize: 0` fallback, `holdSize` 1.25 x `PackScale.Factor` drew a 0.44 m extinguisher over the whole leaf, 36 cells. `PortalContentBuilder.PackSize` now authors 0.54 m — its true 0.4445 m model rounded up to the next 0.09 m pitch plus a cell, the frame every mat-tuned item on the roster is in — giving **2 x 4 = 8 cells**, which every face but `LongGoods` takes strictly. `holdSize` and the pose in the hand are untouched, and `PackSizeTests` carries the divergence with its reason (an unlisted one fails that sweep).  **`RuinScanner` was, and the sign came off the buttons.** A pistol-grip survey unit stood on the rear face of its body slab with the emitter at the sky (8x3). Its Blender frame names its own up — screen plate and top button on +Z, grip and four ribs down -Z, emitter housing at +Y — and the prefab's model instance turns that by (90, -90, 0), landing the emitter axis on the item's +Y. `-90` about X lays it on a flank: 8x6, the device's real silhouette. Screen-UP is not on the menu and is not the answer — the grip and its pommel hang 0.91 m below the screen plane in the model's own metres (z 0.6795 down to z -0.2285, on a 1.13 m long axis), so screen-up balances on the pommel. The two flanks are mirror images to within 0.07% of face area, so neither sign is upside down; it is settled by what the player sees, and the +X flank carries the three control buttons (one red, two amber) against the -X flank's single brass dial.
- **`ItemPackOrientation.Verify` used to assume every entry lands on identity**, because the first four did. An entry whose `Expected` is not the exact inverse of its `Rotation` — a prefab with a hand-authored `rotationOffset`, like `RuinScanner`'s (0, 90, 0) — then logged `saved` and `FAILED` on the same run, for landing exactly where it was told to. It now derives the landing from the entry (`Landing`), so a row cannot disagree with its own check.
- **Laying a long item down costs it faces.** A pole standing on its tip reserves a stub; laid down its footprint is its LENGTH, and on the rig that fits only `Rack` (whose overhang is `u` ONLY, ski-fashion) or a back panel (both axes). `LongGoods` is one cell deep and takes nothing wider than a cell. That is the honest price of an item that reads like an object rather than a token, and it is worth knowing before "fixing" the next one.
- **A uv typed as a round number is not a spot on the grid.** The layout stores the *snapped* uv, and a swap hands the displaced item the vacated placement's stored uv — so a test that lays gear down at `(0.60, 0.45)` and then asserts it came back "where the player aimed" compares an asked uv with a snapped one and fails by up to half a cell (the leaf has a hem across it, so a round number was never on the lattice). Name spots with `PackGrid.BlockCentreUv`/`CentreUv`, as `Backpack{Stow,Swap,Networking}Tests` do. And do not assert a hem with `Assert.AreEqual(Vector2.zero, …)`: that comparison is bitwise while `30 * PackGrid.Cell` and an authored `4.05` need not be the same float, and it prints `(0.00, 0.00)` against `(0.00, 0.00)` — see [Testing](Testing.md).
- **A lashing is one to three bands, and the count is a COUNT.** `PackStrapVisual.BandCount` brackets on the item's long-axis cells (`SingleBandCells` 2, `ThirdBandCells` 6) and the stations are the even fractions of the footprint — one at 50%, two at 25/75, three at 1/6, 1/2, 5/6, matching the holder art's own convention. It was once one band per interior cell *boundary*, which lashed a ten-cell staff under nine ribbons and read as a net. Do not put `PackScale` on the brackets: the cell scales with the rig and an item measures in cells, so the metres they stand for already move. `PackStrapVisualTests` pins the three brackets. Design basis: the mat is a diegetic interface and the ITEM is the information the player reads — webbing is chrome, and enough of it to hide the silhouette inverts the hierarchy (`GDC-L1-UX-0003`).
- **`ItemGrip.packSize` is NOT metres on the mat.** It is authored at the item's honest size next to the hand, and `ItemFootprint.Measure` multiplies `PackScale.Factor` in — once, in one place. Typing a pre-multiplied number into the prefab gives an item 2.25x on the mat with nothing to say why. The same trap in reverse: do not "fix" a too-small item by editing `holdSize`, which is the hand's number and is on `ItemScaleLadder`'s bracket table.
- **An item sized against a FACE has to be derived from that face, not typed.** The wing pack is the folded ornithopter and is meant to fill the rack — so `WingPackBuilder.PackSizeForRack` solves its `packSize` from the rack's own width (9 cells x 0.96 fill), the folded mesh's short:long proportions and `PackScale.Factor`, and never states a length. Its hand-computed predecessor was right when it was written and wrong from the moment the pack was first resized, leaving the craft at six of nine columns with nothing but "that looks small" to say so. **The face's width is a ceiling, not a preference**: one column over and the rack refuses it outright *and* the gear wall — strict on both axes — cannot take it either, so the item becomes unstorable everywhere. Along the overhang axis there is no ceiling; that is what makes it a rack. `WingPackStowTests` pins both ends. **And an item sized against one face has to be CONFINED to it**, or it is storable in places it was never sized for: the back panels overhang on both axes, so `PackOverhang.Clamp` shrinks *any* oversized rectangle down to their own 3x6 span and reports it as fitting — which let the whole folded aircraft be strapped to a panel the leaf covers the moment the pack closes, invisible and unflyable, with green cells all the way. [`ItemGrip.ConfinedToSurfaces`](Assets/Game/Scripts/Items/Equipped/ItemGrip.cs) is the other direction of `AcceptsOnly`: empty for every item but this one, and enforced in the same single place, `PackSurface.AcceptsItem`, so every path that already consults a reserved face consults this too. The wing pack names `Rack` and `WallGrid`, the only two faces it is sized against.
- **A length in the pack's own frame must go through `PackScale`.** Grid line widths, strap widths, carry lift, the focus camera's standoff, `ItemFootprint`'s `ClipSize`/`Implausible`/`Unmeasurable` thresholds — all of them are metres on the mat and all of them scale. An angle, a count, a fraction and a duration must NOT. `Implausible` in particular: it was 2 m, "wider than any surface on the rig", and the lash line is 18 cells, which passes 2 m at any `Factor` above 1.11.
- **A length in the wall's frame is in the DRAWN frame or the LOGICAL frame, and you have to say which.** (`PackSurface.ToLocal` also divides out `lossyScale`, because the FBX is on the centimetre convention — `PIVOT_Back` arrives with `Lcl Scaling` **100** and every `SURF_` empty and every `Marker_` under it inherits it. Skip the divide and a 0.4 m uv lands 40 m away; any mesh built under a surface **or a marker** must use this exact frame. **Half a divide is worse than none**: `PackHose` took its tube's LENGTH back from `InverseTransformPoint`, already in the marker's frame, so the hose reached the bottle perfectly — while its 14 mm radius was raw metres and drew **2.8 m across**, a near-black slug (`Mat_Plastic_Rubber_Black`, #1A1A1A) wider than the whole 1.81 m rig, appearing only once a bottle went into the socket and reading as a modelling mistake rather than an arithmetic one. Fixed 2026-09-04; `PackHoseTests` measures the thickness **and** the reach, because a guard on either one passes the other's bug.) Anything going through `PackSurface.ToLocal`/`ToWorld` (grid lines, strap widths, ghost lift) is logical and is scaled for you. Anything computing a world offset *itself* is drawn and must multiply `surface.DisplayScale` in — `BackpackItemVisual`'s copy scale, `HolderBuilder`'s fit, `PackHandVisuals.CarryLift`. Anything reading world space *back* must divide it out — `PackSurface.ToUv` and `PackStrapVisual.SampleGeometry`, whose sampled silhouette is handed straight back to `ToLocal`. Miss the divide in `ToUv` and the wall is unpointable; miss it in `SampleGeometry` and a band wraps thin air beside the item.
- **`PlayerShipBuilder.WallDepth` is a MEASUREMENT of the whole fitting, not `TRAY_D` times a scale.** It was derived from the tray, on the assumption the tray reaches furthest back; a 2026-09-01 hand edit to the `.blend` deepened `Mesh_Wall_Surround` (object scale 1.7966 on Y) past it, so the builder believed 0.36 while the fitting really reached 0.6468 and stood 0.29 m nearer the hull than intended — the bottom of its plinth inside the hull skin's baked collision, with nothing anywhere to say so. `inventory_wall_scale.py` now measures and prints the real back reach; take it from that printout.
- **`inventory_wall.blend` carries hand edits the generator does not have** — a `Plane` backing panel, reassigned materials, and two meshes at deliberate non-identity object scale. **Never run `inventory_wall.py` over it.** `inventory_wall_scale.py` is safe: it touches mesh data and locations only, composes against its `wall_scale` stamp instead of refusing, and now *reports* non-identity meshes rather than aborting on them — it still hard-fails on a non-identity **empty**, because `SURF_WallGrid` must stay unscaled or every display copy Unity parents under it is rescaled. It composes **downward** too: a second refusal ("shrinking is not what this pass is for") meant the only way to take an over-scale back out was to comment the guard out, which is the guard in the wrong shape one step on from the one it replaced. A residual under 1 divides exactly the meshes a residual over 1 multiplied.
- **Resizing the gear wall is one constant, two builders, one re-measure.** Move `PackScale.WallDrawn`, re-run the wall builder then the ship builder (the placement constants ride the constant), then restate `WallInventoryTests.TheWallIsDrawnAtItsDecidedSize`'s decided ratio and re-run `PlayerShipTests`' wall probes. The `.blend` stays untouched — its baked `WallModel` never moves. Changing the CELL COUNT is the expensive lever: `SurfaceCellsAcross`/`Up` and `inventory_wall.py`'s `GRID_W`/`GRID_H` together, in whole cells and in multiples of six (a bay), and that regenerates a hand-edited `.blend`. `PlayerShip_InventoryWallStaysInsideItsDecidedOverheadIntrusion` measures headroom from the DECK up so a wall already through the roof cannot pass by starting its rays above it.
- **Regenerating the rig `.blend` is three steps, not two** — generate, dress, then [`expedition_rig_scale.py`](Assets/Game/Art/Models/_Source~/components/props/expedition_rig_scale.py). That last one stamps `scene["rig_scale"]` with the scale the file is at and **composes**: it applies `SCALE / stamped` and refuses only a file already at `SCALE`. So changing `PackScale.Factor` is `SCALE = <new>` plus one run, on the shipped `.blend`, never a regenerate. (It used to refuse any stamped file outright, which was the right guard in the wrong shape: a shrink then needed the refusal commented out, which is exactly how a 2.25x rig that no number on Unity's side agrees with gets shipped.) It touches mesh data and object locations only, so hand edits survive it. Generate into `components/props/` itself and rename, never into a scratch directory: the palette is a LINKED library and a relative path generated elsewhere does not resolve once the file is copied back. **And `Mesh_Rig_LashRail` is load-bearing outside this system now:** `BackpackController.GearMount` hands that transform to [BodyEquipment](BodyEquipment.md), which seats worn back gear on it and lights it up as the clickable mount on the gear screen — so renaming the part, or moving its origin off the middle of the lash line, silently moves where every worn wing pack sits. `gearMountPartName` is the one string that names it. (`SURF_LongGoods` is a pack surface on that same rail; the two do not collide only because `IsExteriorWhenStowed` is `Rack` alone, which folds the rail's own face inward while the pack is worn.) **And the rig no longer models an oxygen bottle.** `Mesh_Rig_OxygenTank` and `Mesh_Rig_OxygenTank_Bands` were authored as "a fixed fitting, not an item — the composition's landmark"; once a real carryable bottle existed ([Oxygen.md](Oxygen.md)) that landmark was a bottle on the player's own pack that nothing could take off, which is how it was reported. Both were deleted from the `.blend` BY NAME (never a regenerate — see above) and from `expedition_rig.py`, and the rig carries a real `OxygenTank` in its starting items instead. `Mesh_Rig_OxygenTank_Manifold` deliberately stays: it is bolted to the panel rather than to the bottle and carries the rig's only emissive. Record in `expedition_rig_BUILD.md`.
- **Rebuilding the rig prefab wipes hand edits.** `ExpeditionRigWiring.Build` reads the starting-item lists forward and re-verifies the saved prefab, because Unity discards prefab saves silently when the AssetDatabase is read-only.
- Rotation in the hand ignores `allowRotation` on purpose; that row only constrains authored shapes and first-fit. **`PackLayout.OnChanged` is coarse** — no index, because a placement can change face. Every change tears down and rebuilds *all* display copies, holders, cell rings and straps; `AdoptPlacements` sets `rebuilding` to suppress the storm and rebuilds once at the end. **`PackGridVisual` keeps one stale flag per PASS, not one shared**, and `MarkDirty` raises both: the lattice and the socket invitation draw on *different faces in the same frame* and each clears its own flag, so a single flag would be cleared by whichever ran first and leave the other early-outing on geometry that change had already invalidated — a socket still lit over cells another player just filled (`PackSocketInviteTests.ALayoutChangeRebuildsTheInvitationEvenAfterTheLatticeHasRun`). And **a stow is never re-aimed**: `TryStowFromHotbar` has no first-fit fallback, because the player only ever sends cells they watched turn green.
- Coverage lives in [Tests/Editor](Assets/Game/Tests/Editor) (`PackScaleTests`, `PackLayoutTests`, `PackShapeTests`, `PackSurfaceTests`, `PackSizeTests`, `PackHandTests`, `PackLeafDragTests`, `PackStrapVisualTests`, `PackHoseTests`, `PackSocketInviteTests`, `WallInventoryTests`, `Backpack{Stow,Swap,Fold,SaveCodec,DeployArc,Solidity}Tests`, `WornHiddenTests`) and [Editor/Tests/](Assets/Game/Editor/Tests) (`BackpackNetworkingTests`, `PackOrientationTests`, and for the shared primitives `FocusFlightTests`, `DisplayCopyTests`).

## Extending

**Make a new item placeable** — 1) Give the prefab an `ItemGrip` with a sane `holdSize` (or `packSize`); without one the mesh bounds are believed. 2) Nothing else is required: the derived block from `PackShape.ForFootprint` works immediately. 3) Only if it is not a rectangle, run `Tools/SpaceGame/Items/Create Pack Shape Library`, then draw the mask in the `PackShapes.asset` inspector grid ([`PackShapeLibraryEditor`](Assets/Game/Scripts/Items/Backpack/Placement/Editor/PackShapeLibraryEditor.cs)). 4) Watch for the `PackShapes:` warning that says the mask is smaller than the item. 5) Verify it lays out on a client, and reload a save with it on the mat.

**Add a holder surface** — 1) Add the `SURF_` empty in [`expedition_rig.py`](Assets/Game/Art/Models/_Source~/components/props/expedition_rig.py) and re-export through all three steps; author its rectangle as a whole number of cells in that file's own **modelling** frame (0.09 m), which `expedition_rig_scale.py` then prints multiplied. 2) Append a `PackSurfaceId` value (never renumber). 3) Add the row to `ExpeditionRigWiring.SurfaceTable` — at `PackGrid.Cell`, i.e. the `.py`'s number times `PackScale.Factor` — and mirror it in `PackGrid`'s doc table. 4) Decide `PackOverhang.Axes` for it — default is strict. 5) Add a `Reaches` case if it rides a hinge (`PIVOT_Leaf` children are hidden when racked) and an `IsExteriorWhenStowed` case only if the fold genuinely exposes it. 6) Re-run `ExpeditionRigWiring.Build` and read its `VERIFIED` line. 7) Confirm gear on it survives a save/load and appears on a joining client.
