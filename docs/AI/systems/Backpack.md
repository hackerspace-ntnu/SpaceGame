# Backpack

The physical inventory: a deployable expedition rig whose seven flat faces are cell grids you lay real items onto, rummaged in from a dedicated focus camera.

**Scope:** [`Assets/Game/Scripts/Items/Backpack/`](Assets/Game/Scripts/Items/Backpack) (+ [`Focus/`](Assets/Game/Scripts/Items/Backpack/Focus), [`Placement/`](Assets/Game/Scripts/Items/Backpack/Placement), [`Holders/`](Assets/Game/Scripts/Items/Backpack/Holders)), [`Assets/Game/Editor/Backpack/`](Assets/Game/Editor/Backpack), [`ExpeditionRig.prefab`](Assets/Game/Prefabs/Items/Equipment/ExpeditionRig.prefab), [`expedition_rig.fbx`](Assets/Game/Art/Models/Props/expedition_rig.fbx) / [`.blend`](Assets/Game/Art/Models/_Source~/components/props/expedition_rig.blend).
**Related:** [Inventory.md](Inventory.md) (item defs, hotbar — not repeated here), [Multiplayer.md](Multiplayer.md), [Persistence.md](Persistence.md).

## Model

- The pack is a **plain `Instantiate` per player** parented to the spine bone — not a spawned `NetworkObject`. Contents replicate as *state*, not as objects. Deploy unparents it; reshoulder reparents.
- Contents live on the **pack**, not the player: a pack set down keeps its gear.
- An item is `(itemId, PackSurfaceId, uv in metres, yaw)`. No slots, no indices — an index means nothing because a placement carries its own face and position.
- **One global 0.135 m cell** ([`PackGrid.Cell`](Assets/Game/Scripts/Items/Backpack/Placement/PackGrid.cs)), read off the rig's own webbing pitch. All 7 faces are exact multiples of it (Leaf 8x8, Rack 9x9, LongGoods 18x1, Back 3x6 each, Wings 4x7 each = **255 cells**, zero hem). Capacity is *cells occupied*, not a count and no longer a raw-area or diagonal test.
- **The gear wall alone is DRAWN 1.06x its own grid** ([`PackScale.WallDisplay`](Assets/Game/Scripts/Items/Backpack/Placement/PackScale.cs)) since 2026-09-01. Unlike `Factor` this moves nothing but pixels — see [Drawn frame vs logical frame](#drawn-frame-vs-logical-frame).
- **The whole thing is drawn at [`PackScale.Factor`](Assets/Game/Scripts/Items/Backpack/Placement/PackScale.cs) = 1.5** since 2026-09-01. One factor on every *length* — cell, faces, the `.blend`, the gear wall, the size each item is drawn at, the focus camera's standoff — and none on any *count*. It is a similarity transform, so 255 cells are still 255 cells, every authored mask is still valid, and nothing about capacity moved; what moved is how much of the screen the pack fills. See [Scale](#scale).
- Each item fills a **mask** ([`PackShape`](Assets/Game/Scripts/Items/Backpack/Placement/PackShape.cs)) — authored in [`PackShapes.asset`](Assets/Game/ScriptableObjects/Items/PackShapes.asset), else derived by ceiling its measured footprint to whole cells. Masks let two L-shapes interlock.
- Layout logic ([`PackLayout`](Assets/Game/Scripts/Items/Backpack/Placement/PackLayout.cs), `PackGrid`, `PackShape`) touches no `UnityEngine` beyond `Vector2`, so EditMode tests drive it as plain C#.

## Flows

**Open.** 1) B → `PackFocusSession` + `BackpackController.Toggle` both fire. 2) Toggle only *asks* (`NetMsg.PackState`, request verb). 3) Server re-checks state, runs **its own** ground probe, `Commit` + broadcast. 4) Every machine plays the toss arc, then the unfold. 5) The focus camera flies in 0.15 s later without waiting for the unfold.

**Pick up.** 1) `PackPointer` ray on the `PackItem` layer names the display copy. 2) Left click → `Lift`: purely local, nothing sent — the layout still holds the item; `SetInHand` just stops the pack drawing it. 3) `originGrab` is `AnchorUv` (a cell the item *fills*), not the stored block-centre uv.

**Place.** 1) Every frame `PackLayout.Snap` grid-snaps the cursor uv for the current shape+yaw; `CanPlace` judges *exactly* those cells. 2) `PackGridVisual` paints the footprint green/red plus the whole face's free/taken lattice. 3) Click on green → `LetGo`, then `RequestMove` (from pack) or `RequestStow` (from hotbar) — **nothing moves locally**. 4) Server resolves the grab point positionally, applies, and the `NetworkList` rewrite moves everyone's display.

**Swap.** A full hotbar is not a refusal. `TryTakeToHotbar` puts the pack item in the selected slot and the displaced one back on the pack (same face, then first-fit on that face). A drag onto a *named* slot goes through `BackpackController.TakeIntoSlot`, whose fallback is `TryStow` across every reachable face; `CanTakeToHotbar` predicts both branches so the preview cannot approve a drop the server refuses.

**Flip the leaf.** The one held gesture in focus mode: grab bare board, drag through the arc, release past halfway to commit (`PackLeafDrag`, `BackpackObject.ScrubRack`/`SettleRack`). R is the same thing as a toggle. It only fires where the item hit found nothing.

**Refuse.** There is no message and no cursor change: red cells *are* the refusal. A click on red turns the item a quarter — the refusal and its usual fix are the same click. A symmetric shape with no turn to offer gets a timed flash instead. A click off the faces turns silently. World pickups that overflow use first-fit (`TryStow` → `TryArrange`) across *reachable* faces only.

## Scale

One constant, [`PackScale.Factor`](Assets/Game/Scripts/Items/Backpack/Placement/PackScale.cs) = **1.5**, applied on 2026-09-01. Everything below moved together; anything that did not is a bug.

| Length | Where it is written | Now |
| --- | --- | --- |
| The cell | `PackGrid.Cell` (a literal; `PackScaleTests` asserts it equals `LegacyCell * Factor`) | 0.135 m |
| The 7 rig faces | `ExpeditionRigWiring.SurfaceTable`, mirrored in `PackGrid`'s doc table | Leaf 1.08², LongGoods 2.43x0.135, Rack 1.215², Back 0.405x0.81, Wings 0.54x0.945 |
| The rig model | [`expedition_rig_scale.py`](Assets/Game/Art/Models/_Source~/components/props/expedition_rig_scale.py), a third pipeline step after generate + dress | deployed 2.59 x 3.12 x 1.25 m |
| The gear wall face | `InventoryWallBuilder.SurfaceSize`, as `30 x 22` cells — **re-cut** the same day, see [The wall and the room](#the-wall-and-the-room) | 4.05 x 2.97 m |
| Every item on the mat | `ItemFootprint.Measure`, once, on `ItemGrip.PackSize` | x1.5 |
| Focus camera standoff | `PackFocusCamera.DistanceOut` / `HeightUp` | 3.69 m / 2.25 m |
| Mat decoration | `PackGridVisual`, `PackStrapVisual`, `PackHandVisuals` widths and lifts | x1.5 |
| *(not this factor)* the gear wall's **drawn** board | `PackScale.WallDisplay` + `inventory_wall_scale.py`'s `TOTAL` | x1.06 on top, pixels only — see [Drawn frame vs logical frame](#drawn-frame-vs-logical-frame) |

What deliberately did **not** move: every cell *count*; every angle (`PitchDown`, `Fov`, yaws); `ItemGrip.holdSize` and `packSize` themselves — the item in the hand is exactly the size it was; `BackpackController.deployDistance` / `arcHeight`, which belong to the player's body rather than the pack; and `pack_holders.blend`, because `HolderBuilder` stretches every holder to fit through `ItemFootprint.SizeOf` and so grew on its own. Design basis: the enlargement buys glanceable readability on the mat (`GDC-L1-UX-0003`) and a bigger target for the one gesture focus mode has (`GDC-L1-UX-0004`, `GDC-L1-UX-0007`), and it costs nothing in internal consistency because it is a similarity transform — `GDC-L1-FEEL-0007`'s caution is to keep the simulated space *self*-consistent, which a uniform factor does by construction. An item is still exactly as many cells as it was.

### The wall and the room

The gear wall is the one place the enlargement moved a **count**, because it is the one surface that has to fit inside something. Enlarged in place its fitting came out **8.46 x 4.95 m** and the lander's aft room has neither dimension. **Measure against the baked collision, never against the ribs you can see.** [`player_ship_collision.fbx`](Assets/Game/Art/Models/Vehicles/PlayerShip/player_ship_collision.fbx) is a convex decomposition, and the hull skin `Plane.001` curves up off the deck — its hulls fill that curve, so the outboard half-metre of deck is solid to a player for the first ~0.36 m up while nothing is drawn there. At the old `WallRibClearance` 0.70 the fitting's feet, plinth and tray stood inside it down the whole room. The footprint comes clear at 0.95 m, so the clearance is now **1.00 m**, and at that standoff the headroom over the footprint is **4.37 m** (capped by one arch-rib buttress, `Cube.007`; the deckhead proper is 4.79-4.87 m). The builder centres the fitting on the main deck's centre, which leaves 2.91 m of run forward of it and 3.75 m aft.

So the grid was re-cut, in whole six-cell bays across, from `60 x 30` to **`30 x 22`** — 1800 cells to **660**. That cut is still the capacity; what has moved since is only how big it is *drawn*. As it stands the fitting is **4.675 x 4.102 m** (30 x 22 cells at `PackScale.WallDisplay`), stands on the deck, and leaves **0.282 m** of air above the header cowl against the arch-rib buttress, ~0.26 m clear forward of the cockpit dais riser, ~1.10 m aft and 1.00 m outboard. `WallGridCentreHeight` is **2.1465** (`(GRID_Z0 + GRID_Z1) / 2` x the model's total scale) and `WallDepth` is **0.6856**, the fitting's *measured* back reach rather than `TRAY_D` — both printed by `inventory_wall_scale.py` on every run, and the second of them a fixed defect (see Gotchas). That is a real cut in storage, taken knowingly. A fitting that stands *in* the room reads as part of it; one that clips the deckhead or sinks into the hull destroys the room's legibility, and the deck is the one interior space the player learns (`GDC-L1-LEVEL-0002`, contextual/4). The wall is also read at a glance from across the deck, which is what the 1.5x cell was for in the first place (`GDC-L1-UX-0003`, objective/4) — a bigger cell over a smaller board still wins that trade. The cost is honest and not a design gain: this is a **base store**, deliberately generous, not a scarcity dial, and `GDC-L1-ECON-0002`'s own exception covers exactly that — so 1800 -> 660 is a constraint accepted, not tension bought. It only starts to bite if playtests show the wall filling up; the fix then is a second wall or a bigger room, never a face that does not fit. Nothing is lost from an existing save — see [Persistence](#persistence).

### Drawn frame vs logical frame

`PackScale.Factor` (1.5) and `PackScale.WallDisplay` (1.06) are **not the same kind of number**. `Factor` moved the cell, so it moved every stored uv's meaning and needed a save migration; `WallDisplay` moves nothing but pixels, applies to the gear wall alone, and is applied in exactly three functions — `PackSurface.ToLocal`/`ToWorld`/`ToUv`.
- The **logical frame** is `PackSurface.Size` and its cells — 30 x 22, 4.05 x 2.97 m, 660 — and is what every placement, save byte and wire message is written in. `WallDisplay` never touches it, which is why there is no version bump and nothing to migrate.
- The **drawn frame** is that times `PackContainer.DisplayScale` (a 4.293 x 3.148 m board). The three conversion functions speak it, so the model, ghost cells, hover lattice, display copies, holders, straps and the face `BoxCollider` grow together — and the aim, which resolves through `ToUv`, still lands on the cell under the crosshair.
- **Stated twice, applied once.** `inventory_wall_scale.py` scales the model's geometry by it (cumulatively — `TOTAL` = 1.5 x 1.06, applied as the residual against the `wall_scale` stamp) and `PackScale.WallDisplay` scales the uv->world mapping. One factor in the two frames that must agree: the bay dividers are six cells apart and the webbing on a two-cell pitch, so a model left behind puts every line out of step. Applying it anywhere *else* as well — the prefab root, the surface's local scale — is the double application, and it is silent. Root scaling does not work anyway: `ToLocal` divides `lossyScale` out and the transform multiplies it back, so a uv's world offset is invariant under it and the board would grow while the gear stayed put.
- **1.06 is the room, not a preference.** 1.2 was asked for and does not fit: the fitting is 3.870 m tall, the aft room offers 4.372 m over its footprint (baked collision, at `WallRibClearance`) capped by an arch-rib buttress, and with `PlayerShipTests`' 0.25 m gap the ceiling is `(4.372 - 0.25) / 3.870` = **1.065**. At 1.2 the fitting is 4.644 m and stands 0.255 m *through* the rib; as built the gap is **0.282 m**. Wanting more is a request to re-cut the grid (30 x 18 = 540 cells would take 1.2) or to change the room — never to raise the constant. `WallInventoryTests.TheWallIsDrawnNoLargerThanTheAftRoomAllows` fails on the constant alone, before any rebuild.

## Multiplayer

| Concern | Authority |
| --- | --- |
| Contents (`PackLayout`) | **Server**. Clients never write; `BackpackNetwork` republishes the whole list on `OnChanged` and clients `AdoptPlacements`. |
| Deploy state + drop pose | **Server**, via `NetMsg.PackState` (A = state or `-1` ask, B = request/announce verb). Ground probe is the server's — clients never stream their own chunk. |
| Rack (leaf up) | **Owner-written `NetworkVariable`**. Not contested; focus mode already requires ownership. |
| Take / move / stow | Client asks on the **pack owner's** channel (`PackTake` 68, `PackMove` 76, `PackStow` 78); all handlers are idempotent and positional. |
| Lift into hand | Purely local — no request, no undo needed. |

Nothing about the enlargement crosses the wire. `PackPlacementWire` carries a uv in metres, and both machines derive that uv from the same `PackGrid.Cell` and the same `SurfaceTable` compiled into the same build — so host and client agree by construction, and a mixed-version session was never supported. `PackSurfaceId` values are untouched: the enlargement renumbered nothing. The wall's `WallDisplay` is even further from the wire — it is a serialized field on one prefab, read only by the drawing code.

Other players see the rig, its unfold, every placed item's display copy, holder and straps. An item in someone's hand is hidden on **their** machine only (`SetInHand`); remotes still see it lying on the mat until the server accepts the move.

## Persistence

- `BackpackSaveable` sits on the player (`[RequireComponent(BackpackController)]`), key `backpack`; the format is `BackpackSaveCodec`, testable without a prefab.
- **v3** record = `version (3), itemId, surface (byte), u, v, yaw` + `deployed`/`packPosition`/`packRotation`. Footprints are **never** stored — recomputed from the prefab, so resizing an item does not stale a save.
- **v2 -> v3 is the enlargement.** `u`/`v` are metres, so every uv in a payload with no `version` key (or one `<= 2`) is two-thirds of where it belongs. `Restore` multiplies those uvs by `PackScale.Factor`, which lands each item on the *same cell* it was saved on — scaling a surface and its uv by the same factor is exactly cell-preserving, and `PackScaleTests` asserts it over every origin on an 8x8 face. Without it nothing would be lost (the first-fit fallback below catches it) but the player's gear would silently rearrange itself.
- Restore places each item back exactly, else falls back to `TryArrange` first-fit; only a total failure logs and drops it. A payload with no contents keys at all leaves the pack alone (old saves must not be emptied).
- **Shrinking a face needs no file version, and loses nothing.** The wall's `30 x 22` re-cut put every old placement past its far edge outside the face; `TryPlace` refuses, first-fit catches it, and the item comes back somewhere else on the wall. `WallInventoryTests.GearSavedNearTheOldWallsFarEdgeComesBackOnTheSmallerWall` pins that, because a shrink that silently deleted the far column would look exactly like one that worked. The guarantee is *somewhere legal*, not *where you left it*.
- **The 1.06 wall enlargement needs no file version and no migration at all**, unlike `Factor`'s. It lives entirely in the drawn frame, so a wall save written before it is byte-identical to one written after and reopens on exactly the same cells. `WallInventoryTests.AWallSaveDoesNotNoticeTheEnlargementAtAll` asserts both directions — same JSON, same uvs back.
- v1 (`strapItemIds`/`mainItemIds` compartments) migrates through first-fit. Free-placement uvs and 24°/45° yaws from before the grid land on the nearest cell/quarter-turn — no second file version.
- Redeploy is deferred to `OnLoadComplete` and goes **straight to the settled pose**, never through an arc.

## Gotchas

- **A worn pack is hidden from its own wearer's camera, and nothing about that is tunable geometry.** `BackpackController` registers `Pack.GetComponentsInChildren<Renderer>(true)` with [`PlayerLook.SetWornHidden`](Assets/Game/Scripts/Characters/Player/Movement/PlayerLook.cs) — 35 renderers on the bare rig, more with gear — and clears it again. Three call sites, all reading `Pack.IsWorn` so none of them has to agree about which of the four states counts as "on the back": `SnapToWorn` (on), `StartDeploy` (off, at the FIRST frame of the toss — the toss is staged in front of the player so they watch it, so it must be visible for the whole flight and not from the landing), and `OnPackVisualsRebuilt` (the gear, which is instantiated under the rig long after either). **Do not try to fix an intruding pack by moving `wornLocalPosition` instead.** The pack rides the `Spine` bone while the camera is bolted to the player root at `(0, 1.45, 0.16)`, so a walk cycle's lean rotates it about a pivot below the eye and throws its top forward through the near plane — and `LongGoods` takes an item **2.43 m** long, so no worn pose survives gear the player chose the size of. The 2026-09-01 `PackScale.Factor` enlargement is what first pushed it past the threshold: the stowed board went from 0.81 m to 1.215 m and `wornLocalPosition` was never re-tuned, which is a real and separate thing to look at from *outside* first person.
- **The magnet is gone.** `CanPlace` answers about the exact cells drawn, never a nearby spot. Do not reintroduce "find the nearest legal spot" — comments and [BackpackStowTests](Assets/Game/Tests/Editor/BackpackStowTests.cs) exist to keep it out. The ghost cache is keyed on `(surface, cell origin, legal, rect dims)`, and masked shapes bypass the early-out entirely because `Rotated` allocates a new pattern per call.
- **Class-level comments still say "the limit is surface area."** That is legacy prose from the pre-grid design; the real limit is cell occupancy.
- **`Reaches` gates player paths only.** `TryPlace`/`AdoptPlacements`/`StowAuthored` deliberately ignore it, or a restore onto a worn pack (every pack is worn in `Awake`) would lose everything not on the Rack. `Rack` is the *only* face reachable while stowed; the leaf, lash line and both wings ride `PIVOT_Leaf` and vanish when racked.
- **The layout is keyed by item ID.** The same asset can never be in the pack twice — lifts from the hotbar are refused up front rather than dying at the drop.
- **`PackSurface.ToLocal` divides out `lossyScale`.** The FBX is on the centimetre convention; skip the divide and a 0.4 m uv lands 40 m away. Any mesh built under a surface must use this exact frame.
- **Holder FBX axes are baked, not rotated.** `pack_holders.fbx` imports with `bakeAxisConversion: true` and `ExpeditionRigWiring.NormaliseRoot` folds any residual root rotation into children. `HolderBuilder` stretches a holder non-uniformly and counter-scales `HARD_` children componentwise — that inverse is only valid when axes agree, so a rotated `HARD_` empty comes out sheared.
- **An item with no `ItemGrip` measures its raw mesh bounds** (one shipped prefab came out 11 m and filled the screen). `ItemFootprint` warns once per prefab past 2 m. `PackSize` falls back to `HoldSize`, whose default 0.30 m must stay equal to `EquipItemSocket.DefaultHoldSize`.
- **The footprint cache never expires by itself** — [`ItemFootprintCacheInvalidator`](Assets/Game/Scripts/Items/Backpack/Placement/Editor/ItemFootprintCacheInvalidator.cs) clears it on asset import. `PackShapeLibrary` re-indexes on `OnValidate`.
- **An item keeps its own up.** `FootprintOf` is *defined* as `(size.x, size.z)`; a prefab that lies down wrong is authored data — fix it with [`ItemPackOrientation`](Assets/Game/Editor/Backpack/ItemPackOrientation.cs), not at seating time. For a **builder-owned** prefab the turn goes in the builder instead, or the next run swallows it without a word — [`JumpingRodBuilder.LieDown`](Assets/Game/Editor/Items/JumpingRodBuilder.cs) is the worked example — and it turns the CARRIED prefab only: `JumpingRodDeployed.prefab` is a planted pogo stick, must stay standing, and the hop hangs it by a *measured* `bounds.min.y`, so laying the carried one down cannot reach the bounce. Either way, compensate `ItemGrip.rotationOffset` by the inverse: `rotation = handRotation * Euler(offset)`, so turning the contents by R and the offset by R inverse multiplies back out and **the pose in the hand does not move**.
- **"Smallest axis up" is not the same as "the way you would put it down".** Maximising the resting face is right for a slab, a pole or a board and wrong for anything with a grip, a sight or a foot: a rifle set on a table rests on its magazine, not on its side. And even where the axis is settled the SIGN is not — +90 and -90 about X both lay an item down and one of them lays it down upside down. `Tools/SpaceGame/Items/Audit Pack Orientation (whole roster)` prints the measurement and names the candidate axis; the sign is decided by looking.
- **The axis and the sign are both decidable off the mesh — go and measure before turning anything.** Neither needs the Editor: drive Blender headlessly over the `.blend` in `_Source~/`, or over the FBX for a model with no source, and read the geometry. Two settled cases, both done that way:
  - **`PortalGun` is NOT mis-oriented, however the audit reports it.** It is a fire extinguisher, so its longest axis is its own up and the audit says "STANDS ON END". It has a **foot**: 0.0130 m² of down-facing geometry in the bottom 5 mm of the mesh, an annulus from r 0.018 to r 0.0505 m against a bottle radius of 0.0589, and `portal_gun.py` puts the origin at the centre of that ring so the bottle "stands on a surface without a Z nudge". Laying it down turns 4x9 cells that fit the rack strictly into 14x9 that fit nothing, which `PackOverhang` then lashes ski-fashion across **every one of the rack's 81 cells** — a third of the rig for one item. And the sign is undecidable in any case: the mesh is mirror-symmetric about X to within 0.07% of face area (+X 0.042826 m², -X 0.042858 m²), so the only thing the choice picks is which sight tube gets buried. `PortalGunWiringTests.TheGunStandsOnItsBaseRing` pins it, and `PortalContentBuilder` carries the numbers. What genuinely read wrong there was the **size**, and it is fixed: through the `packSize: 0` fallback, `holdSize` 1.25 x `PackScale.Factor` drew a 0.44 m extinguisher 1.875 m tall on a 1.08 m leaf for 36 cells. `PortalContentBuilder.PackSize` now authors 0.54 m — its true 0.4445 m model rounded up to the next 0.09 m pitch plus a cell, the frame every mat-tuned item on the roster is in — giving **2 x 4 = 8 cells**, which every face but `LongGoods` takes strictly. `holdSize` and the pose in the hand are untouched, and `PackSizeTests` carries the divergence with its reason (an unlisted one fails that sweep).
  - **`RuinScanner` was, and the sign came off the buttons.** A pistol-grip survey unit stood on the rear face of its body slab with the emitter at the sky (8x3). Its Blender frame names its own up — screen plate and top button on +Z, grip and four ribs down -Z, emitter housing at +Y — and the prefab's model instance turns that by (90, -90, 0), landing the emitter axis on the item's +Y. `-90` about X lays it on a flank: 8x6, the device's real silhouette. Screen-UP is not on the menu and is not the answer — the grip and its pommel hang 0.91 m below the screen plane in the model's own metres (z 0.6795 down to z -0.2285, on a 1.13 m long axis), so screen-up balances on the pommel. The two flanks are mirror images to within 0.07% of face area, so neither sign is upside down; it is settled by what the player sees, and the +X flank carries the three control buttons (one red, two amber) against the -X flank's single brass dial.
- **`ItemPackOrientation.Verify` used to assume every entry lands on identity**, because the first four did. An entry whose `Expected` is not the exact inverse of its `Rotation` — a prefab with a hand-authored `rotationOffset`, like `RuinScanner`'s (0, 90, 0) — then logged `saved` and `FAILED` on the same run, for landing exactly where it was told to. It now derives the landing from the entry (`Landing`), so a row cannot disagree with its own check.
- **Laying a long item down costs it faces.** A pole standing on its tip reserves a stub; laid down its footprint is its LENGTH, and on the rig that fits only `Rack` (whose overhang is `u` ONLY, ski-fashion) or a back panel (both axes). `LongGoods` is one cell deep and takes nothing wider than a cell. That is the honest price of an item that reads like an object rather than a token, and it is worth knowing before "fixing" the next one.
- **A uv typed as a round number is not a spot on the grid.** The layout stores the *snapped* uv, and a swap hands the displaced item the vacated placement's stored uv — so a test that lays gear down at `(0.60, 0.45)` and then asserts it came back "where the player aimed" compares an asked uv with a snapped one and fails by up to half a cell (the leaf has a hem across it, so a round number was never on the lattice). Name spots with `PackGrid.BlockCentreUv`/`CentreUv`, as `Backpack{Stow,Swap,Networking}Tests` do. And do not assert a hem with `Assert.AreEqual(Vector2.zero, …)`: that comparison is bitwise while `30 * PackGrid.Cell` and an authored `4.05` need not be the same float, and it prints `(0.00, 0.00)` against `(0.00, 0.00)` — see [Testing](Testing.md).
- **A lashing is one to three bands, and the count is a COUNT.** `PackStrapVisual.BandCount` brackets on the item's long-axis cells (`SingleBandCells` 2, `ThirdBandCells` 6) and the stations are the even fractions of the footprint — one at 50%, two at 25/75, three at 1/6, 1/2, 5/6, matching the holder art's own convention. It was once one band per interior cell *boundary*, which lashed a ten-cell staff under nine ribbons and read as a net. Do not put `PackScale` on the brackets: the cell scales with the rig and an item measures in cells, so the metres they stand for already move. `PackStrapVisualTests` pins the three brackets. Design basis: the mat is a diegetic interface and the ITEM is the information the player reads — webbing is chrome, and enough of it to hide the silhouette inverts the hierarchy (`GDC-L1-UX-0003`).
- **`ItemGrip.packSize` is NOT metres on the mat.** It is authored at the item's honest size next to the hand, and `ItemFootprint.Measure` multiplies `PackScale.Factor` in — once, in one place. Typing a pre-multiplied number into the prefab gives an item 2.25x on the mat with nothing to say why. The same trap in reverse: do not "fix" a too-small item by editing `holdSize`, which is the hand's number and is on `ItemScaleLadder`'s bracket table.
- **An item sized against a FACE has to be derived from that face, not typed.** The wing pack is the folded ornithopter and is meant to fill the rack — so `WingPackBuilder.PackSizeForRack` solves its `packSize` from the rack's own width (9 cells x 0.96 fill), the folded mesh's short:long proportions and `PackScale.Factor`, and never states a length. Its hand-computed predecessor was right when it was written and wrong from the moment the pack went to 1.5x, leaving the craft at six of nine columns with nothing but "that looks small" to say so. **The face's width is a ceiling, not a preference**: one column over and the rack refuses it outright *and* the gear wall — strict on both axes — cannot take it either, so the item becomes unstorable everywhere. Along the overhang axis there is no ceiling; that is what makes it a rack. `WingPackStowTests` pins both ends.
- **A length in the pack's own frame must go through `PackScale`.** Grid line widths, strap widths, carry lift, the focus camera's standoff, `ItemFootprint`'s `ClipSize`/`Implausible`/`Unmeasurable` thresholds — all of them are metres on the mat and all of them scale. An angle, a count, a fraction and a duration must NOT. `Implausible` in particular: it was 2 m, "wider than any surface on the rig", and the lash line alone is 2.43 m now.
- **A length in the wall's frame is in the DRAWN frame or the LOGICAL frame, and you have to say which.** Anything going through `PackSurface.ToLocal`/`ToWorld` (grid lines, strap widths, ghost lift) is logical and is scaled for you. Anything computing a world offset *itself* is drawn and must multiply `surface.DisplayScale` in — `BackpackItemVisual`'s copy scale, `HolderBuilder`'s fit, `PackHandVisuals.CarryLift`. Anything reading world space *back* must divide it out — `PackSurface.ToUv` and `PackStrapVisual.SampleGeometry`, whose sampled silhouette is handed straight back to `ToLocal`. Miss the divide in `ToUv` and the wall is unpointable; miss it in `SampleGeometry` and a band wraps thin air beside the item.
- **`PlayerShipBuilder.WallDepth` is a MEASUREMENT of the whole fitting, not `TRAY_D` times a scale.** It was derived from the tray, on the assumption the tray reaches furthest back; a 2026-09-01 hand edit to the `.blend` deepened `Mesh_Wall_Surround` (object scale 1.7966 on Y) past it, so the builder believed 0.36 while the fitting really reached 0.6468 and stood 0.29 m nearer the hull than intended — the bottom of its plinth inside the hull skin's baked collision, with nothing anywhere to say so. `inventory_wall_scale.py` now measures and prints the real back reach; take it from that printout.
- **`inventory_wall.blend` carries hand edits the generator does not have** — a `Plane` backing panel, reassigned materials, and two meshes at deliberate non-identity object scale. **Never run `inventory_wall.py` over it.** `inventory_wall_scale.py` is safe: it touches mesh data and locations only, composes against its `wall_scale` stamp instead of refusing, and now *reports* non-identity meshes rather than aborting on them — it still hard-fails on a non-identity **empty**, because `SURF_WallGrid` must stay unscaled or every display copy Unity parents under it is rescaled.
- **The gear wall is sized by the ROOM, not by the cell.** It is the one face whose cell count is a measurement of somewhere else — see [The wall and the room](#the-wall-and-the-room). Change `SurfaceCellsAcross`/`Up` and `inventory_wall.py`'s `GRID_W`/`GRID_H` together, in whole cells and in multiples of six (a bay), then re-run both builders; `PlayerShip_InventoryWallStopsShortOfTheOverhead` is what tells you it still fits, and it measures headroom from the DECK up so a wall already through the roof cannot pass by starting its rays above it.
- **Regenerating the rig `.blend` is three steps, not two** — generate, dress, then [`expedition_rig_scale.py`](Assets/Game/Art/Models/_Source~/components/props/expedition_rig_scale.py). That last one stamps `scene["rig_scale"]` and refuses a file that already carries one, because a second pass leaves a 2.25x rig that no number on Unity's side agrees with and nothing downstream reports it. Generate into `components/props/` itself and rename, never into a scratch directory: the palette is a LINKED library and a relative path generated elsewhere does not resolve once the file is copied back.
- **Rebuilding the rig prefab wipes hand edits.** `ExpeditionRigWiring.Build` reads the starting-item lists forward and re-verifies the saved prefab, because Unity discards prefab saves silently when the AssetDatabase is read-only.
- Rotation in the hand ignores `allowRotation` on purpose; that row only constrains authored shapes and first-fit.
- **`PackLayout.OnChanged` is coarse** — no index, because a placement can change face. Every change tears down and rebuilds *all* display copies, holders, cell rings and straps; `AdoptPlacements` sets `rebuilding` to suppress the storm and rebuilds once at the end.
- **A stow is never re-aimed.** `TryStowFromHotbar` has no first-fit fallback: the player only ever sends cells they watched turn green.
- Coverage lives in [Tests/Editor](Assets/Game/Tests/Editor) (`PackLayoutTests`, `PackShapeTests`, `PackSurfaceTests`, `PackSizeTests`, `PackHandTests`, `PackLeafDragTests`, `PackStrapVisualTests`, `Backpack{Stow,Swap,Fold,SaveCodec,DeployArc}Tests`, `WornHiddenTests`) and [Editor/Tests/](Assets/Game/Editor/Tests) (`BackpackNetworkingTests`, `PackOrientationTests`).

## Extending

**Make a new item placeable** — 1) Give the prefab an `ItemGrip` with a sane `holdSize` (or `packSize`); without one the mesh bounds are believed. 2) Nothing else is required: the derived block from `PackShape.ForFootprint` works immediately. 3) Only if it is not a rectangle, run `Tools/SpaceGame/Items/Create Pack Shape Library`, then draw the mask in the `PackShapes.asset` inspector grid ([`PackShapeLibraryEditor`](Assets/Game/Scripts/Items/Backpack/Placement/Editor/PackShapeLibraryEditor.cs)). 4) Watch for the `PackShapes:` warning that says the mask is smaller than the item. 5) Verify it lays out on a client, and reload a save with it on the mat.

**Add a holder surface** — 1) Add the `SURF_` empty in [`expedition_rig.py`](Assets/Game/Art/Models/_Source~/components/props/expedition_rig.py) and re-export through all three steps; author its rectangle as a whole number of cells in that file's own **modelling** frame (0.09 m), which `expedition_rig_scale.py` then prints multiplied. 2) Append a `PackSurfaceId` value (never renumber). 3) Add the row to `ExpeditionRigWiring.SurfaceTable` — at `PackGrid.Cell`, i.e. the `.py`'s number times `PackScale.Factor` — and mirror it in `PackGrid`'s doc table. 4) Decide `PackOverhang.Axes` for it — default is strict. 5) Add a `Reaches` case if it rides a hinge (`PIVOT_Leaf` children are hidden when racked) and an `IsExteriorWhenStowed` case only if the fold genuinely exposes it. 6) Re-run `ExpeditionRigWiring.Build` and read its `VERIFIED` line. 7) Confirm gear on it survives a save/load and appears on a joining client.
