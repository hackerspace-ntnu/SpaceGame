# humanoid_base — build record

**File:** `Assets/Game/Art/Models/_Source~/models/creatures/humanoid_base.blend`
**Generator:** `humanoid_base.py`

A neutral, mid-detail humanoid **sculpting base**: 1.75 m, androgynous, four limbs,
full five-finger hands, block feet, on a **Mixamo-compatible armature matching
`AstronautArmature.fbx`**. It is a canvas, not a finished character — the user
sculpts on it.

## What it is for, and why that changes the rules

Every other asset in this library is a finished, transform-applied, faceted or
decimated deliverable. A sculpting base is the opposite thing, and two of the
library conventions are deliberately not met:

| Convention | Status here | Why |
| --- | --- | --- |
| Faceted / low-poly | **Not met** — 100 % quads, smooth, subdividable | A sculpt cage must subdivide cleanly. Triangles do not. |
| Origin at connection point | Origin at **floor centre** (0,0,0) | For a whole character the floor centre under the pelvis *is* the logical pivot, and it is what the armature roots to. |

Transforms *are* applied (object scale 1.0). A live `Subdivision` modifier sits on
top at **viewport level 0 / render level 2** — it is the smoothing level to raise
while sculpting, and it is deliberately 0 in the viewport so the cage is editable.

## How it is built — a skinned stick figure, not bridged tubes

The mesh is generated by laying out a **graph of edges** (a stick figure of ~90
nodes) and running the **Skin modifier** over it, then subdividing. The Skin and
Subsurf modifiers are then **applied**, and the result is welded and normalised.

This matters, and the first version of this script got it wrong. Building each
limb as its own bridged tube and pushing them against the torso produced a mesh
with **88 boundary edges** — the limbs were separate open shells that merely
touched the body. That is unsculptable (there is a hole under every armpit) and
it breaks bone-heat weighting, which is the same class of failure recorded in
`vrescal_sculpt_BUILD.md`. Skinning a connected graph welds every junction by
construction, and the shipped mesh verifies at **0 boundary edges**.

Two consequences worth knowing before editing the node graph:

- **Skin radii are `(along-X, along-Z)` in the plane perpendicular to the chain.**
  For the vertical spine that is *(width, depth)*; for the horizontal arm it is
  *(depth, height)*; for the foot, which runs along Y, it is *(width, height)*.
  Reading them as a single "thickness" is how the torso first came out a
  featureless cylinder.
- **Below roughly 0.012 m a branch collapses into its parent.** The fingers were
  originally authored at 0.009 m and simply did not exist in the output; they are
  now 0.013–0.016 m. If a detail vanishes, this is the first thing to check.

## Rig — matched to the astronaut, exactly

`AstronautArmature.fbx` is a **Mixamo rig: 65 bones, `mixamorig:` prefix**, imported
into Unity as `animationType: 3` (Humanoid) with `avatarSetup: 1`. The base
reproduces that hierarchy bone-for-bone and name-for-name, so:

- Unity builds the same Humanoid Avatar from it, and
- `AstronautArmature.controller` retargets onto it without remapping.

```
mixamorig:Hips
├── mixamorig:Spine → Spine1 → Spine2
│   ├── mixamorig:Neck → Head → HeadTop_End
│   ├── mixamorig:LeftShoulder  → LeftArm  → LeftForeArm  → LeftHand  → 5 × 4-bone fingers
│   └── mixamorig:RightShoulder → RightArm → RightForeArm → RightHand → 5 × 4-bone fingers
├── mixamorig:LeftUpLeg  → LeftLeg  → LeftFoot  → LeftToeBase  → LeftToe_End
└── mixamorig:RightUpLeg → RightLeg → RightFoot → RightToeBase → RightToe_End
```

Finger chains are `Thumb1..4`, `Index1..4`, `Middle1..4`, `Ring1..4`, `Pinky1..4`
per hand — Mixamo's own naming, where the `*4` bone is the fingertip terminator.

### The astronaut's scale is a trap, and this file does not repeat it

Measured out of the FBX, the astronaut's skeleton stands **3.028 m** tall in
Blender space with the armature object at **scale 0.01**. That is not a 3 m
astronaut: the FBX is authored in centimetres, `useFileScale: 1`, so Unity's unit
conversion divides by 100 on import and the character lands at human height. The
Blender-space number is a pre-conversion authoring artefact.

This base is authored at **true metres — 1.75 m, object scale 1.0, feet on z = 0**,
which is the library convention and is what `humanoid_robot.blend` also does. Its
export must therefore *not* reuse the astronaut's centimetre pipeline.
Bone proportions are taken from the astronaut **as ratios**, scaled to 1.75 m:

| Landmark | Astronaut (blend) | ÷ 3.028 | This base (m) |
| --- | --- | --- | --- |
| HeadTop | 3.0184 | 0.997 | 1.7450 |
| Head | 2.2801 | 0.753 | 1.3178 |
| Shoulder | 2.1706 | 0.717 | 1.2545 |
| Hips | 1.2868 | 0.425 | 0.7437 |
| UpLeg | 1.1908 | 0.393 | 0.6882 |
| Foot | 0.2010 | 0.066 | 0.1162 |

## Decomposition — one mesh, and why

**No component files were created, and none were reused.** That is a departure
from the library default and it is deliberate:

- The `components/organic/` parts (`limb_segment`, `haunch`, `foot_pad`,
  `claw_talon`, `scute_plate`) are **Vrescal anatomy** — a quadruped/hexapod
  desert animal. None is a human limb, and scaling one into a human arm would
  produce the exact defect `humanoid_robot_BUILD.md` already flags about its own
  arms ("reads as pauldrons rather than as arms").
- More fundamentally, **a sculpting base must be one continuous watertight
  surface**. Multi-object assembly is the correct answer for hard-surface
  machines and the wrong answer here: sculpting across an object seam is not
  possible, and Dyntopo/Multires need a single mesh.

So the deliverable is a single `Mesh_HumanoidBase_Body`. If limbs are ever needed
as separate reusable pieces, that is a different asset with a different purpose.

## Variations

Two collections:

| Collection | Verts | What it is |
| --- | --- | --- |
| `Coll_HumanoidBase_Cage` | 6 904 | Even, untapered limb masses. The neutral canvas. |
| `Coll_HumanoidBase_Anatomical` | 6 776 | Same graph with the deltoid, biceps, thigh, calf and glute nodes thickened ~9 % and the waist pinched. The shipped default. |

They are **not** vertex-order-identical — the Skin modifier retopologises around
each junction, so changing a radius changes the vertex count. Blending between
them with a shape key is therefore not possible; pick one and sculpt it.

## Measured on the shipped file

```
Mesh_HumanoidBase_Cage          1.441 x 0.213 x 1.745 m   6 904 verts · 6 888 quads
Mesh_HumanoidBase_Anatomical    1.441 x 0.213 x 1.745 m   6 776 verts · 6 760 quads
both:  0 tris · 0 ngons  (100 % quads)
       0 boundary edges · 0 non-manifold · 0 loose verts
       0 unweighted verts · 65 vertex groups
armature HUMANOIDBASE_Rig       65 bones · object scale 1.0
sole on z = +0.000 · crown at z = 1.745 · armspan 1.441 m
```

100 % quads and a watertight shell are the two properties that make it sculptable;
0 unweighted verts is what makes the bind usable immediately.

### The bind is verified by posing, not by counting

Weight counts alone do not prove a rig works, so the build is checked by rotating
bones and measuring the **evaluated mesh**:

```
LeftForeArm +60° about Z   ->  hand moves 0.137 m
Head        +35° about X   ->  skull moves 0.071 m
```

Two traps this caught, both worth keeping:

- **Rotating the forearm about Y moves nothing.** The arm runs along X, so Y is
  its *roll* axis. An early check read that 0.004 m as a broken bind; the rig was
  fine and the test axis was wrong.
- **Bone heat silently dropped 12 finger bones.** The phalanges are thinner than
  it can resolve, so `Thumb1..3`, `Index3`, `Ring2..3` and `Pinky3` on both hands
  came back with *zero* influence — joints that rotate and move nothing, with no
  warning. `repair_dead_bones()` assigns the nearest 12 verts to any deform bone
  bone heat left empty, and the file now ships **0 real dead bones**.

The 5 bones still carrying no weight are Mixamo's `*4` finger terminators and
`Toe_End`. They are unweighted on the astronaut too and Unity's Humanoid mapping
does not deform with them, so that is correct rather than tolerated.

## Materials

One palette material, `Mat_Hide_Sand_Pale` — an existing Hide-family entry. A
sculpting base is repainted by whoever finishes it, so committing a skin tone here
would be noise. **No material was added to the palette.**

## Not done

- **Not exported to FBX.** A base mesh is a source asset; it has no place in
  `Assets/Game/Art/Models/Characters/` until a character is sculpted from it.
- **No animation clips.** It borrows the astronaut's, via Humanoid retargeting.
- **No `COL_` collision boxes** — matching `humanoid_robot`.
