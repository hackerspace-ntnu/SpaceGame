# Procedural World Generation

Two independent edit-time generators — marching-cubes **terrain features** and SDF **caves** — plus a ring-based **settlement generator** and the runtime **site registry** NPCs navigate by.

**Scope:** [`Assets/Game/Scripts/World/ProceduralGeneration/`](Assets/Game/Scripts/World/ProceduralGeneration) (Terrain, Cave, Settlement), [`World/Sites/`](Assets/Game/Scripts/World/Sites), [`World/Caves/`](Assets/Game/Scripts/World/Caves), [`Assets/Game/Editor/Terrain/`](Assets/Game/Editor/Terrain).
**Related:** [WorldStreaming.md](WorldStreaming.md) · [NavMeshSystem.md](NavMeshSystem.md) · [Environment.md](Environment.md) · [InteriorScenes.md](InteriorScenes.md)

## Model

- **Nothing generates the base heightmap.** Unity `Terrain` heightmaps are authored/sliced by the chunker ([`WorldChunkerEditor`](Assets/Game/Editor/World/WorldChunkerEditor.cs), `Tools/World Streaming/Chunk World`) — see [WorldStreaming.md](WorldStreaming.md). Everything here *adds* geometry on top of that terrain.
- **Terrain features** = designer drops a spawner, drags a footprint polygon, picks Mesa or Cliff → a density field → marching cubes → skirt-blended onto the terrain → **baked to a `.asset` mesh**. Runtime only instantiates.
- **Caves** = seeded random-walk room/corridor graph → smooth-min SDF → marching cubes → NavMesh. Baked mesh + `NavMeshData`; decoration/liquid/lights still run at spawn.
- **Settlements** come in two flavours, both edit-time only, output baked into the scene:
  - The Clanker town uses a `RobotSettlementRecipe` ScriptableObject (building prefabs, per-role counts, ring radii) → [`RobotSettlementGenerator`](Assets/Game/Scripts/World/ProceduralGeneration/Settlement/Spawning/RobotSettlementGenerator.cs) places a core building, then rings of buildings/scenery/patrols/vehicles by raycast-seated placement.
  - Everything else uses the general-purpose [`Settlement`](Assets/Game/Scripts/World/ProceduralGeneration/Settlement/Core/Settlement.cs) component (subclassed by [`DesertSettlement`](Assets/Game/Scripts/World/ProceduralGeneration/Settlement/Biomes/DesertSettlement.cs)): one `SettlementConfig` ScriptableObject (building/decoration/character prefab+count lists, scatter radius, spacing, terrain-shaping knobs) scattered around the component's own transform by a seed **derived from that transform's position** — not stored anywhere — so one config asset placed at many different spots produces a different, still-reproducible layout at each one. [`SettlementTerrainSculptor`](Assets/Game/Scripts/World/ProceduralGeneration/Settlement/Core/SettlementTerrainSculptor.cs) then pins the terrain flat under each building with a blended margin and fills the rest with gentle seeded noise, so the settlement doesn't read as a flat disc.
- **Determinism**: every generator is a pure function of one `int` seed plus serialized settings. `System.Random(seed)` (cave graph) or hash/Perlin off the seed (terrain features). One exception — `RobotSettlementGenerator` uses global `UnityEngine.Random` and only calls `Random.InitState` when `useSeed` is ticked, so an unseeded reroll is not reproducible.
- **The one placed `RobotSettlementGenerator` is the mock Clanker settlement**, in a main-world chunk under a root named `ClankerSettlement`, seeded (`1701`), from `ClankerSettlement.asset`. The recipe's `outriderPrefabs`/`outriderTotal` are mounted units on their own slots (two `ClankerOutrider`s), placed *after* everything else so adding them did not move a seeded town. Each robot group is a band — `AssignFormation` gives its members one `FormationModule` id (`<scene>/<root>/group<n>`, an instance override the scene saves) and makes the first the leader, so a group patrols as a group. The generated garrison is the town's *starting* population; `SettlementPopulation` on the root ([AgentSystem.md](AgentSystem.md)) tops it up to its own `maxPopulation` a wave at a time afterwards.
- **This is the only settlement generator left.** A tile-composing generator (`SettlementGenerator`/`SettlementLayout`/`SettlementBuilder`/`SettlementDetailPlacer`, plus a `NomadSettlementGenerator` that scattered finished building prefabs in concentric bands for nine world towns) existed through 2026-09-26 and was deleted along with every settlement it had placed, keeping only the Clanker settlement above. If you find a doc, plan, or spec still describing tile settlements or nomad towns, it is describing removed code.
- **Authored, not generated**: [`WorldSiteMarker`](Assets/Game/Scripts/World/Sites/WorldSiteMarker.cs) components are hand-placed; they publish `WorldSite` records into a static registry NPCs query.
- **Airborne sites opt out of ground search.** A marker's `airborne` flag (the Sky City's, set by `SkyCitySettlementWiring`) makes `WorldSiteRegistry.TryFindNearest`/`TryFindRandom`/`Query` skip it by default — those are what `NpcTaskModule`'s home search and `NpcTaskPlanner`'s task destinations call. `WorldSiteRegistry.TryFindByName` ignores the flag, for a caller that already knows the place by name rather than searching by kind.

## Flows

**Terrain feature (edit time → bake):**
1. `TerrainFeatureSpawner.BuildContext()` — resolves the terrain sampler (`targetTerrain` else `Terrain.activeTerrain`), calls `FeatureFootprint.Refresh(seed)`, builds the `FeatureContext`.
2. `TerrainFeatureRegistry.Create(type)` → `feature.ApplySettings(SyncFeatureSettings())`.
3. [`TerrainFeatureGenerator.Generate`](Assets/Game/Scripts/World/ProceduralGeneration/Terrain/Core/TerrainFeatureGenerator.cs): `AdaptSmoothingToDetail` (eases Laplacian smoothing as `detailStrength` rises) → `BuildDensity` → `TerrainMarchingCubesMesher.Build` → `TerrainSkirtBlend.Apply(embed: 1)`. Mesh named `<Type>_seed<N>`.
4. Editor **Bake & Save Mesh** writes `<scene folder>/TerrainFeatureBakes/<Type>_seed_<N>_<globalObjectId hex>_Mesh.asset` and assigns `bakedMesh`. Save the scene.

**Terrain feature (runtime):** `Awake` → if playing, enqueue on `ChunkActivationQueue.Shared` (spreads PhysX collider cooks across frames); `SpawnBaked()` when a baked mesh exists, else `GenerateNow()` (slow, iteration only). One child `TerrainFeature_<Type>_seed<N>` with MeshFilter/Renderer/MeshCollider on `featureLayer`.

**Cave:** `CaveGraphGenerator.Generate(settings, rng)` → `CaveSdfField` → `MarchingCubesMesher.Build` → (profile path) `LiquidPoolFinder.Find`. `CaveSpawner.Awake` uses baked mesh + `NavMeshData` when present, else generates live; then always spawns liquid pools, cluster lights, entrance tube + `CaveExitCover`, and runs `DecorationScatterer`.

**Settlement (Clanker):** `RobotSettlementGenerator.Generate()` → `Clear()` any previous `Generated` root → seed `UnityEngine.Random` if `useSeed` → place the shield generator dead-center → inner ring (barracks/eco hubs), mid ring (satellite dishes), outer ring (turrets) either on evenly-spaced slots (`organizedLayout`) or by random-annulus retry (`TryPlaceBuilding`) → scatter scenery rocks → spawn robot patrol groups (each given a `FormationModule` band) → park vehicles → place outriders last (so an existing seed's earlier layout never shifts).

**Settlement (general-purpose):** `Settlement.Generate()` → `Clear()` (restores any previous terrain backup, then destroys the `Generated` root) → creates `root` with its scale set to cancel the placing GameObject's own `lossyScale`, so nothing spawned under it — buildings included — ever inherits that transform's scale → seed = `SettlementPlacementUtil.SeedFromPosition(transform.position)` → three placement layers, each spawned strictly after the previous one, each with its own exclusion list so a later layer never fights an earlier one for room:
  1. **Buildings** scatter directly under `root` by seeded rejection sampling in a disk of `config.radius` (`SettlementPlacementUtil.SeededRng`, never `UnityEngine.Random`), kept clear of each other by a mesh-derived footprint circle (`SettlementPlacementUtil.ClearanceRadius`, `config.minSpacing` added on top) — solid architecture needs real room.
  2. `SettlementTerrainSculptor.Shape` flattens the ground under the placed buildings and blends/noises the rest, returning a backup stored on the component.
  3. **Decorations** (tents, etc.) spawn under their own child transform, sampling ground *after* the sculpt. They keep clear of *only each other*, by a flat `config.decorationSpacing` gap (not their mesh size) — a large canopy is allowed to sit close to, or overlap, its neighbours — and keep out of a building's actual collider geometry via a real `Physics.OverlapSphere` check against that building's spawned hierarchy (`SpawnEntries`' `avoidSolidsOf` parameter), never a building's footprint circle.
  4. **Characters** spawn last, under their own child transform, so they get whatever room buildings and decorations left. Same treatment as decorations: a flat `config.characterSpacing` gap between characters instead of a mesh-derived footprint circle (so a crowd can stand close together), plus the same real-collider check against buildings only.
  Decorations get no collision check of any kind, since the tent kit has nothing solid to collide with. `DesertSettlement` only overrides `GetSpawnRotation` (face-center).

## Multiplayer

**Baked and shipped, not replicated.** Terrain-feature meshes and cave meshes/NavMeshData are `.asset` files referenced from chunk scenes; settlement output is plain scene GameObjects. Every machine loads the same bytes, so no netcode is involved and nothing here is a `NetworkBehaviour`. Cave decoration/liquid/light spawns run per machine but are seeded off `ctx.Seed ^ rule.seedSalt`, so they agree. Divergence risks: an *unbaked* `TerrainFeatureSpawner` or `CaveSpawner` regenerates locally (identical only because the seed is serialized — `CaveSpawner.randomSeedOnStart` breaks that outright), and `RobotSettlementGenerator` is an edit-time tool whose global-`Random` output must be committed to the scene, never rolled at runtime.

## Persistence

- **Nothing generated is saved.** Meshes are assets; placements are scene content. Regeneration is a designer action, not a load-time one.
- `WorldSiteRegistry` is pure runtime state, cleared on play start and on world unload. It is *not* serialized — but `WorldSiteMarker.id` is, and NPC saves reference it (`NpcGroup.Record.lastSiteId`), so the id is derived from scene+hierarchy via `SaveableEntity.DeriveAuthoredId` rather than a fresh GUID. Changing a marker's hierarchy path orphans saved references.
- See [Persistence.md](Persistence.md); the feature/cave/settlement systems register no savers.

## Gotchas

- `TerrainFeatureType` integers are **deliberately non-contiguous** (`Mesa = 2`, `Cliff = 4`) — twelve unused entries were deleted and scenes store the int. Never renumber; only append. A stale int makes `TerrainFeatureRegistry.Create` return null → warning, no mesh.
- **This doc's predecessor described features that no longer exist** (ArchingCave, BadlandsMaze, Boulders, dunes, spline/path features, `VoxelSdfDensity`, multi-mesh `BuildMeshes`, `FlatPadFeature`). Only Mesa and Cliff remain, single-mesh only.
- A null `targetTerrain` silently falls back to `Terrain.activeTerrain` — during a bulk bake that skirt-blends features onto the **wrong ground height** and they bake off-screen. Run `TerrainGenManager.AutoAssignTerrains` first.
- Bake filenames include a `GlobalObjectId` because two same-type/same-seed spawners previously baked to the same path and the second bake deleted the first's mesh asset.
- `featureSettings` is `[SerializeReference] object`; a newly-added nested reference field deserialises as `null` on old scenes — that is what `TerrainFeature.HealSettings` exists to repair.
- `TerrainFeatureSpawner.OnAfterDeserialize` migrates pre-rewrite fields; it tests the legacy polygon with `IsValid` (≥3 verts), because a non-null empty `[Serializable]` object would re-run migration forever and revert footprint edits.
- `HeightfieldDensity` without a `coverageFn` meshes the **whole box** — you get a flat ground apron around the feature. Uncovered columns must report `HeightfieldDensity.NoColumn` (`-1e9`).
- `TerrainSkirtBlend` uses a fixed 1.5 m `ContactBand` and deliberately ignores `overlap`; `overlap` means only the feature's own edge falloff (`TerrainNoiseHelper.OverlapWeight`).
- Surface detail finer than ~2× `voxelSize` cannot survive meshing; `AdaptSmoothingToDetail` already relaxes smoothing, so don't hand-tune both.
- `CaveSpawner` generates in `Awake`, not `Start`, so its entrance `InteriorAnchor` exists before `InteriorManager` places the player — moving it drops the player at the origin.
- **A settlement placed in a chunk makes the world NavMesh stale, and nothing in the chunk says so.** The mesh is one author-time bake ([NavMeshSystem.md](NavMeshSystem.md)); new buildings are not in it until `World/Streaming/Bake World NavMesh` runs again, so the garrison stands still on ground the mesh still thinks is open, and `WorldNavMeshBuildCheck` fails the next build.
- **A mesa is invisible to an editor raycast.** Terrain-feature meshes are spawned at bake time, not kept in the chunk scene, so `RobotSettlementGenerator.SampleGround` (a `Physics.Raycast`) and `Terrain.SampleHeight` both report the flat terrain *under* a mesa. Anything that chooses ground in the editor must read `TerrainFeatureSpawner.Area.ComputeLocalBounds()` and keep out of it, which is what the settlement builder does.
- **`RobotSettlementGenerator` raycasts with `terrainMask = ~0`, so a later placement can land on an earlier one.** Terrain is on layer `Default` like the buildings, so the mask cannot separate them; the ring radii and `buildingPadding` are what keep buildings apart, and a parked vehicle can still end up on a roof.
- `WorldSiteMarker` **never unregisters on disable** (a caravan may be walking to a site whose chunk unloaded); only `WorldSiteRegistry.Clear()` removes sites.
- **`Settlement`'s seed is the placing GameObject's own position, not a stored field** — deliberately, so one `SettlementConfig` dropped onto many GameObjects gives each a different-but-reproducible layout instead of cloning the same one. Moving the GameObject changes the layout; there is no `Reroll` (compare `RobotSettlementGenerator`, which has one and pays for it with `UnityEngine.Random`'s own non-reproducibility gotcha above).
- **`Settlement.Generate()` always restores its previous terrain backup before shaping again.** Regenerating without this would compound: every Generate call would flatten/noise on top of the last one's already-modified terrain. The backup (per-terrain height patch) is a hidden serialized field on the component — deleting the `Settlement` component without first calling `Clear()` leaves that patch of terrain permanently modified.
- **A `Settlement`'s `radius + blendDistance` is a soft ceiling of one terrain chunk (500×500 m, `WorldChunkerEditor.cs:26`).** `SettlementTerrainSculptor.Shape` loops `Terrain.activeTerrains` so it *will* edit a neighboring chunk's tile if the settlement straddles the boundary, but only tiles that are currently loaded — an unloaded neighbor silently keeps its old heights, leaving a seam when that chunk streams in later. Keep settlement centers well clear of chunk edges.
- **A `Settlement`'s buildings make the world NavMesh stale**, same as the Clanker town (see the NavMesh gotcha above) — run `World/Streaming/Bake World NavMesh` after generating.
- **Everything a `Settlement` places — buildings, decorations, characters, all of it — renders at exactly its own prefab's authored scale. `Generate()` never adjusts it, on principle.** `root` cancels the placing GameObject's own `lossyScale` the moment it's created (`root.localScale = 1/lossyScale`), before anything spawns under it, so no descendant can inherit whatever scale the `Settlement` transform happens to carry. **This is a one-way invariant, not a per-category default** — do not reach for a scaled parent transform, a per-`SpawnEntry` scale field, or any other placement-time scale knob to make an under- or over-sized prefab read right; fix the prefab itself instead (as `NomadSail_*` was — see ArtPipeline.md's Gotcha).
  - History, so the same mistake isn't reintroduced: through 2026-09-27 buildings were *deliberately* left inheriting the `Settlement` transform's own scale, because the nomad building kit is modelled at roughly half human scale and that scale was how it was made to read right — the placed `"Settlement"` in `Chunk_7_5.unity` still carries `m_LocalScale: 7.28789` for exactly that reason. `decorations`/`characters` got a scale-cancelling parent to opt back out of it. That asymmetry is what let `Raxy.asset`'s ten `NomadSail_HexLow` decorations render at ~7× their already-corrected height when only `characters` had the cancelling treatment. The user asked for the stronger, unconditional guarantee above instead of chasing categories one at a time. **Consequence: any building prefab still authored at the kit's half scale now renders half-size in a settlement whose transform used to compensate for it** (e.g. `Chunk_7_5.unity`'s `7.28789`-scaled `"Settlement"`) — that scale multiplier no longer reaches anything it places. Undersized buildings need the same fix `NomadSail_*` got (a baked-in root scale on the building's own wrapper prefab), not a reason to bring container scaling back.
- **`SettlementPlacementUtil.ComputeFootprint` used to divide a prefab's own root scale back out, silently reporting the footprint it would have at scale 1.** It measured mesh-corner positions in `prefab.transform`'s local space via `root.InverseTransformPoint`, which inverts root's full matrix — translation, rotation, *and scale*. Harmless while every prefab root was scale 1 (true everywhere except `NomadSail_*`, whose root now deliberately carries a corrected scale — see ArtPipeline.md), but on those it reported 1.5-3× the real footprint, reserving that much placement space for nothing. Fixed by axis-aligning against root's position/rotation only (`Matrix4x4.TRS(root.position, root.rotation, Vector3.one)`), which correctly includes root's own scale in the measured size.
- **A settlement's own large decorations can starve themselves (or its characters) under a mesh-derived footprint circle, and the fix is placement logic, not settlement `radius`.** Raxy's ten `NomadSail_HexLow` tents (15×14.7 m real footprint each — see ArtPipeline.md) mutually exclude each other by half their longest mesh dimension (~7.6 m) if spaced by `SettlementPlacementUtil.ClearanceRadius` the way buildings are — two of them alone need centers 15 m+ apart, so packing ten into a 10 m-radius disk is geometrically impossible and only the first placement ever lands, with a clean console (`TryPlace` failing is silent by design). The same shared exclusion list previously let a tent's oversized footprint circle exhaust every one of a character's 30 placement attempts too. Neither decorations nor characters were ever meant to be spaced like buildings. The fix (2026-09-27, generalized 2026-09-27): buildings, decorations, and characters are three separate placement layers, each with its own `Placement` list — decorations and characters keep clear of *only their own kind*, using a flat `config.decorationSpacing`/`config.characterSpacing` gap instead of a mesh-derived footprint circle, and keep out of buildings via a real `Physics.OverlapSphere` against each spawned building's actual collider hierarchy instead (`Settlement.OverlapsAnySolid`, fed the `Transform`s collected while spawning `config.buildings`) — never a building's footprint circle. So a tent can now overlap a neighbouring tent, and a character can stand under a tent or right beside a building, without literally overlapping a wall. Decorations get no collision check at all. **If a decoration ever gains real solid geometry** (unlike the open sail canopies), this stops being safe and it needs the same `avoidSolidsOf` treatment buildings get, not a blanket exemption.
- **A `SpawnEntry.prefab` must be the wrapper `.prefab` under `Assets/Game/Prefabs/...`, never the raw model asset under `Assets/Game/Art/Models/...`.** Both are draggable into the same `GameObject` field and Unity gives no warning either way, but only the wrapper carries any prefab-level fixes (material overrides, the `NomadSail_*` height correction) — the raw FBX's implicit prefab has none of them. `Raxy.asset`'s `decorations[0]` pointed at `nomad_sail_hex_low.fbx` instead of `NomadSail_HexLow.prefab` until 2026-09-27, so the tents it placed carried none of the standalone-prefab height fix regardless of the scale-cancelling bug above; `buildings[0]` (guid `c7c30737bd024451784e3a45a58e6edf`, `count: 0` so currently inert) has the same mistake and was left alone because its nearest wrapper prefab (`NomadBuilding_02.prefab`) turned out to wrap a *different* source FBX — re-pointing it needs a human to confirm which building was actually meant.
- **A `Home` site is not automatically a ground destination.** `SiteKind` says what a place is FOR, not whether anything can walk to it — the Sky City is `Home` because that is what it is to the Sky Tribe, but it sits 228 m up with no ground link. With its marker's `airborne` flag set, every kind-based search (`WorldSiteRegistry.TryFindNearest`/`TryFindRandom`/`Query`) skips it **for everyone, including the Sky Tribe's own errands** — `airborne` is not "ground NPCs only", it opts the site out of kind search entirely. Only `TryFindByName` (a caller that already knows the place by name) or an explicit `includeAirborne: true` finds it. Before the flag existed, nothing stopped `NpcTaskModule.EnsureHome`/`NpcTaskPlanner.ResolveDestination` from sending an unrelated ground NPC there; a new elevated or otherwise unwalkable structure needs the same flag, not a new `SiteKind`.
- Feature/cave meshes feed the shared world NavMesh through their `MeshCollider` layer — they get no isolated `NavMeshData` (except a baked cave's). The layer must be one the world surface collects; see [NavMeshSystem.md](NavMeshSystem.md).

## Extending

**New terrain feature type**
1. Append an entry to `TerrainFeatureType` with a fresh integer (do not reuse or reorder).
2. Subclass `TerrainFeature`: implement `FeatureType`, `DensityKind` (prefer `Heightfield`), `BuildDensity`. Copy [`MesaFeature`](Assets/Game/Scripts/World/ProceduralGeneration/Terrain/Features/MesaFeature.cs) as the template.
3. Shape the silhouette with `context.FootprintDistanceInside(x, z)` → `TerrainNoiseHelper.OverlapWeight`; never hardcode a box edge. Pass a `coverageFn` to `HeightfieldDensity`.
4. Seed everything off `context.Seed` (`Hash01`, `Fbm`); no `Time`, no `UnityEngine.Random`.
5. Optional knobs: a `[System.Serializable]` settings class + `CreateDefaultSettings` / `ApplySettings` (+ `HealSettings` if it nests reference blocks).
6. Add one arm to `TerrainFeatureRegistry.Create`. Spawner, inspector, handles and bake pipeline need no changes.
7. Bake in a chunk scene, verify the NavMesh rebuild, commit the mesh asset and the scene.

**New cave pass** — add a static pass class in the matching folder and call it from `CaveGenerator.Generate` after the existing passes; take `System.Random rng` (or the seed) as a parameter rather than creating your own, so the whole pipeline stays one seeded sequence.

**New settlement placement rule (Clanker town only)** — add a step to `RobotSettlementGenerator.Generate`, drawing its prefabs/counts from a new `RobotSettlementRecipe` field. Draw its random numbers *last*, after every existing step, so an already-seeded town's layout does not shift when the new step ships.

**New settlement (anything else)** — don't extend `RobotSettlementGenerator`; that generator is the Clanker town specifically. Instead: create a `SettlementConfig` asset (buildings/decorations/characters + layout/terrain knobs), drop a `Settlement` (or a biome subclass like `DesertSettlement`) on a GameObject, assign it, right-click → Generate. A new biome only needs a new `Settlement` subclass overriding `GetSpawnRotation` (and any future per-biome hook) — it must not add its own serialized field if it can help it; the point of this hierarchy is that the whole thing configures through one `SettlementConfig`.

**New site kind** — add a `SiteKind` entry, give it a gizmo colour in `WorldSiteMarker.KindColour`, place markers, and query it via `WorldSiteRegistry.TryFindRandom` (prefer random over `TryFindNearest`, which makes every NPC walk the same route). If the new site cannot be reached on foot, tick `airborne` on its marker instead of inventing a kind for it.
